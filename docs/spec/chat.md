# AI 대화

## 상황 목록
- 코드 상수(`src/lib/scenarios.ts`)로 둔다. 레벨당 7개, 총 35개이며 영어와 일본어가 같은 목록을 쓴다. 처음에는 레벨당 4개였다. 2026-10-18 하루 1세션 사용자가 D7 전에 같은 상황을 되풀이하지 않도록 7개로 늘렸다(ADR-019). 첫 마디가 고정이라 같은 상황을 다시 하면 더 똑같이 느껴진다. 상황은 코드 상수라 늘려도 운영비는 그대로다.
- 레벨 안의 순서는 정해져 있다. 기존 4개를 그대로 두고 그 뒤에 새 3개를 붙인다. 앞 3개는 Free 상황이고, 4~7번째는 Pro 상황이다(`usage.md` "Pro 상황"). 순서를 바꾸면 무료 상황이 바뀌므로 상황을 더할 때는 맨 뒤에 붙인다. 상황 `id`는 세션에 저장되므로 바꾸거나 다시 쓰지 않는다.
- 2026-10-18에 더한 15개(사용자 승인, 제목. 목표·역할·첫 마디는 초안을 사람이 검수한다). 잠금·Pro 구현 phase 전에 기존 상황과 같은 모양(번역·`pronKo`·`alignBreakdown` 모양의 `breakdown` 포함)으로 `scenarios.ts`에 넣는다. 초안은 자동 검사(뜯어보기·한글 발음 단위 테스트)를 통과하도록 고친 뒤 사람이 검수한다. 내용과 잠금·Pro 로직은 함께 main에 병합한다. 로직만 먼저 배포하면 Free 사용자는 기존 4번째 상황만 잠기고 새 상황은 없기 때문이다:

  | 레벨 | 5번째 | 6번째 | 7번째 |
  |---|---|---|---|
  | 입문 | 택시에서 목적지 말하기 | 좋아하는 것 이야기하기 | 친구와 약속 시간 정하기 |
  | 초보 | 공항에서 체크인하기 | 관광 안내소에서 추천 받기 | 미용실에서 원하는 스타일 말하기 |
  | 중급 | 병원 접수하기 | 이웃에게 택배 맡아 달라고 부탁하기 | 분실물 신고하기 |
  | 상급 | 부동산에서 계약 조건 확인하기 | 동료와 업무 일정 조율하기 | 이웃에게 소음 문제 정중하게 말하기 |
  | 고수 | 상사에게 퇴사 의사 전하기 | 화난 고객 응대하기 | 문화 차이를 주제로 깊이 대화하기 |

- 상황마다 `id / 제목 / 사용자 목표`는 공통으로, `AI 역할·배경 / 첫 마디`는 en과 ja 각각 정의한다.
  - 역할·배경과 목표에는 난이도(쉬운 말로 등)를 적지 않는다. 아래 레벨 상황도 지금 레벨 난이도로 말해야 해서, 난이도는 세션 레벨의 지침("레벨별 조절")만 정한다.
  - 첫 마디에는 한국어 번역을 붙이고, 일본어는 후리가나 표기를 포함한다. 일본어 입문~중급 상황(레벨 1~3)의 첫 마디에는 한글 발음(`pronKo`, 아래 "한글 발음")도 붙인다. 상황은 지금 레벨 이하에서만 시작하므로(아래 "대화 진행") 상급·고수 상황은 상급·고수 세션에만 나온다. 그 첫 마디의 발음은 보일 일이 없어 두지 않는다.
  - 초안은 AI로 만들어도 되지만, 사람이 검수한 뒤 코드에 넣는다.
- 문화적 배경은 언어별 데이터에서 사람이 정한다 (예: 영어는 미국 카페, 일본어는 편의점). 첫 마디가 이미 배경을 정하므로 AI가 바꾸지 않는다.

## 대화 진행
1. 지금 레벨 이하의 상황을 고르면 세션을 만들고 **고정된 첫 마디**를 보여 준다.
   - 이때 Claude를 부르지 않는다.
   - 세션의 `level`은 상황의 레벨이 아니라 지금 레벨이다. 아래 레벨 상황도 AI는 지금 레벨의 난이도("레벨별 조절")로 말한다. 레벨을 올린 사용자가 익숙한 상황에서 달라진 난이도를 느끼게 하려는 것이다("레벨 올린 맛"). 첫 마디는 상황에 고정된 문장이라 그 상황 레벨의 쉬운 문장 그대로다. 번역·한글 발음을 보여 주는 방식은 세션 레벨을 따른다.
   - 지금 레벨보다 위 레벨의 상황이면 400 `INVALID_INPUT`이다. 요청한 레벨이 지금 레벨과 다르면(화면을 연 뒤 레벨이 바뀜) 409 `CONFLICT`다.
   - Free 사용자가 Pro 상황으로 세션을 만들면 403 `PRO_REQUIRED`다. Pro 상황인지는 use-case가 상황 상수로 정해 세션 생성 RPC에 넘기고, 플랜은 RPC가 계정을 잠근 뒤 DB 시각으로 판정한다(`usage.md` "Pro 상황").
   - 이미 만든 세션의 턴·종료는 Pro 상황인지 다시 보지 않는다. 체험 중에 시작한 Pro 상황 세션은 체험이 끝난 뒤에도 이어서 하고 끝낼 수 있다. 하루 턴 한도는 그때의 플랜으로 센다.
   - 상황 목록에서 열린 세션(`active`·`ending`)이 있는 상황을 누르면 새 세션을 만들지 않고 그 세션을 연다(`ui.md` "화면별 구성"). 그 세션은 만들 때 저장한 레벨로 이어 간다. 레벨을 올리거나 내린 뒤에도 마찬가지다.
2. 사용자 발화마다 Claude로 응답 하나를 생성하고 아래 구조로 받는다 (zod로 검증). 실패 시 재시도는 `backend.md` "Claude 연동"의 최대 1번 규칙을 따른다.
   ```
   { reply: string,                 // AI의 다음 대사
     reply_ko: string,              // reply의 한국어 번역
     correction: { corrected: string, explanation_ko: string } | null }
   ```
   - 일본어 입문~중급은 `reply_pron_ko`(reply의 한글 발음)와 `correction.corrected_pron_ko`(corrected의 한글 발음)를 더 받는다(아래 "한글 발음"). 그 밖의 언어·레벨은 요청하지 않는다. 그 턴의 `reply_pron_ko`는 `null`로 저장되고 `correction`에는 `corrected_pron_ko` 키가 없다(읽을 때 없는 키는 발음 없음으로 본다).
   - 모든 언어·레벨에서 `reply_breakdown`(reply의 조각 뜻)과 `correction.breakdown`(corrected의 조각 뜻)을 더 받는다(아래 "문장 뜯어보기").
   - 세션의 첫 턴에 후보 단어가 있으면 `target_words`와 `used_words`를, 목표 단어가 있는 세션의 그 뒤 턴은 `used_words`를 더 받는다(아래 "배운 단어 써 보기"). 그 밖의 턴은 요청하지 않는다.
3. 교정은 사용자 메시지 바로 아래에 보여 준다. 틀린 게 없으면(`null`) 보여 주지 않는다.
4. 모든 레벨에서 한국어로 입력해도 된다. 그러면 교정란에 "이렇게 말하면 돼요"가 나온다. 처음에는 입문·초보만 허용했는데, 2026-10-17 운영에서 상급 사용자가 한국어로 입력했을 때 바꾼 문장이 나오지 않아 모든 레벨로 넓혔다(ADR-016). 말이 막힐 때 한국어로 쓰고 바로 배우는 흐름은 레벨과 상관없이 필요하다.
   - 입력에 한국어가 들어 있으면 `correction`은 `null`이 아니다. 한국어 문장이 자연스러워도 마찬가지다. `corrected`는 사용자의 말을 학습 언어로 옮긴 문장이고, `explanation_ko`는 핵심 표현을 짧게 설명한다.
   - 한국어 문장 자체의 맞춤법·표현은 고치거나 평가하지 않는다.
   - 한국 사람 이름·지명은 일본어에서는 가타카나(정대훈 → チョン・デフン), 영어에서는 로마자로 쓴다. 한글을 학습 언어 문장에 섞지 않는다.
5. **한 세션은 최대 20턴이다.** 20번째 응답에 `turnsLeft: 0`이 담겨 오면, 클라이언트가 이어서 `/end`를 호출한다. 대화 응답과 피드백을 한 요청에서 처리하지 않는다.
6. **`/end`는 멱등이다.** 세션 상태는 `active → ending → ended`로 이동한다.
   - 종료 처리 중에는 새 메시지를 받지 않는다. 유효한 턴이 처리 중이면 종료 요청을 409로 거부한다.
   - 이미 `ending`이면 Claude를 다시 부르지 않고 `202 { status: 'ending', retryAfterSeconds: 2 }`를 반환한다. 클라이언트는 화면이 보이는 동안 간격을 두고 `/end`를 재호출하고, 화면에 돌아오면 재개한다.
   - `ended`이면 저장된 피드백과 `feedback_status`를 그대로 반환한다. 처리 실패도 고정 대체 결과로 종료하므로 다음 요청에서 복구할 수 있다.
   - 성공한 턴이 0개인 세션은 Claude를 부르지 않고 `ended`, `feedback_status = skipped`로 끝낸다.
7. **입력은 1~300자다.** 앞뒤 공백을 제거한 뒤 센다. 클라이언트와 서버가 같은 함수(`lib/text`)로 센다.
8. 스트리밍 없이 응답을 한 번에 받는다.
9. **IME 처리**: 조합 중(`isComposing`)일 때 누른 Enter로는 전송하지 않는다. 한글·일본어 입력이 반쯤 전송되는 버그를 막기 위해서다.
10. **음성**: AI 말풍선(첫 마디 포함)과 교정의 고친 문장은 브라우저 음성으로 들을 수 있다. 학습 언어 음성이 없는 기기에서는 버튼을 숨긴다(`audio.md`).

## 대화 1턴 처리 (트랜잭션으로 예약 → AI 호출 → 결과 확정)

한 턴은 `chat_turns`의 한 행이다. 동일 세션의 진행 중인 작업은 하나만 허용한다.

1. 로그인·동의·온보딩 상태와 입력을 확인한다. 세션을 `id + user_id`로 조회하며 없거나 남의 세션이면 404다. 세션에 저장된 언어·레벨로 이어서 대화한다.
2. **예약 RPC**: `profiles` 행을 잠근 뒤 해당 사용자의 만료된 작업을 복구하고 대상 세션을 잠근다. 아래 검사와 예약을 하나의 짧은 트랜잭션에서 처리한다.
   - `status != active`이거나 유효한 `operation_token`이 있으면 409다. `unique(session_id, turn_no)`만으로 실행을 잠그지 않는다.
   - 오늘 `chat_failed`가 10개 이상이면 `429 AI_FAILURE_LIMIT`다.
   - 성공한 세션 턴이 이미 20개면 `409 SESSION_FULL`이다.
   - 오늘 계정의 `pending + done` 턴이 플랜 한도에 도달했으면 예약 없이 `limit_reached`를 기록하고 `429 LIMIT_REACHED`를 반환한다.
   - `turn_no = 마지막 done 턴 + 1`로 `pending`을 생성한다. 그 행의 UUID를 세션 `operation_token`으로 저장하고 `operation_expires_at = DB 현재 시각 + 90초`로 둔다. 커밋 후에도 pending 예약은 한도에 포함된다.
3. **Claude 호출**: DB 잠금을 해제한 뒤 시스템 프롬프트 + 첫 마디 + 순서대로 정렬한 `done` 턴들 + 이번 입력을 보낸다.
4. **성공 확정 RPC**: 같은 잠금 순서로 `active` 상태, 요청의 토큰 일치, 기한 내 처리, 해당 pending 행을 확인한다. 응답 저장·`done` 전환·토큰 해제·활동일/연속일 갱신을 함께 커밋하고 `turnsLeft`를 반환한다. 오늘 예약된 done 턴 수가 한도에 도달하면 같은 트랜잭션에서 `limit_reached`도 기록한다.
5. **실패 확정 RPC**: 해당 작업을 아직 소유한 경우에만 pending 삭제·예약 반환·토큰 해제·`chat_failed` 기록을 함께 커밋한 뒤 `503 AI_UNAVAILABLE`을 반환한다. 재시도까지 실패한 작업당 한 번만 기록하며, `props`에 `operation_token`, `kind(turn/feedback)`, 실패 사유를 넣는다.
6. 이미 복구됐거나 기한이 지난 토큰으로 온 결과는 저장하지 않고 409로 처리한다. 늦은 성공/실패 응답이 새 작업을 변경하거나 같은 실패를 다시 기록해서는 안 된다.

## 처리 중단 복구
- 대화 세션 생성·메시지·종료 API의 쓰기 RPC는 `profiles` 잠금을 잡은 뒤 해당 계정의 만료된 작업을 복구한다. 성공/실패 확정 RPC도 자신의 작업이 만료됐으면 같은 복구 규칙을 적용한다.
- `active`의 만료된 작업: 해당 토큰의 pending 행만 삭제하고 토큰을 해제한다. 실패 이벤트는 한 번 기록하며 사용자는 다시 전송할 수 있다.
- `ending`의 만료된 작업: 아래 고정 대체 피드백으로 `ended`를 확정한다. AI를 다시 호출하지 않는다.
- 기한은 AI 요청 전체 예산(최대 약 40초)과 라우트 실행 상한(60초)보다 긴 90초다. 예약·판정 시각은 DB 기준이며, 복구 뒤 도착한 결과는 토큰으로 차단한다.
- 정리용 cron은 두지 않는다. 아직 처리 기한이 남은 작업은 409/202로 안내하고 만료 뒤 다음 API 요청에서 복구한다. 클라이언트는 표시된 남은 사용량으로 입력을 막지 않고, 서버의 `429` 응답 뒤에만 막는다. 만료된 pending이 표시 사용량에 포함돼 있어도 실제 한도는 서버의 복구 후 판정에 따른다.
- 사용자가 끝내지 않은 유휴 `active` 세션은 자동으로 종료하지 않는다 (`ending` 작업의 만료 복구만 한다).
- 네트워크가 끊긴 뒤 이미 성공한 메시지를 사용자가 다시 전송하는 중복은 MVP에서 감수한다. 메시지 멱등 키는 도입하지 않는다.

## 레벨별 조절
시스템 프롬프트에 레벨 지침을 넣는다.

| 레벨 | AI 문장 | 교정 강도 | 번역 | 일본어 후리가나 | 일본어 한글 발음 |
|---|---|---|---|---|---|
| 입문 | 아주 짧고 쉬운 표현 | 의미가 안 통하는 오류만 | 기본 표시 | 모든 한자·가타카나 | 기본 표시 |
| 초보 | 짧은 문장 | 주요 문법 | 기본 표시 | 모든 한자·가타카나 | 기본 표시 |
| 중급 | 일상 수준 | 문법 + 어색한 표현 | 눌러서 보기 | 모든 한자·가타카나 | 번역과 함께 눌러서 보기 |
| 상급 | 자연스러운 속도 | 뉘앙스까지 | 눌러서 보기 | 모든 한자·가타카나 | 없음 |
| 고수 | 원어민 수준, 관용구 | 뉘앙스·격식까지 | 눌러서 보기 | 모든 한자·가타카나 | 없음 |

- **후리가나**: 일본어는 모든 레벨에서 한자와 가타카나 위에 히라가나 읽기를 단다. 대화(첫 마디·말풍선·교정·종료 피드백), 단어(카드·빈칸 문장·보기·AI 해설), 레벨업 테스트 모두 같다. 가나 익히기 카드에는 달지 않는다(글자를 익히는 연습이라서). 처음에는 입문~중급의 한자에만 달았는데, 2026-10-17 모든 레벨과 가타카나로 넓혔다(ADR-016). 프론트에서 `<ruby>` React 요소로 그린다.
  - 한자: AI가 `[漢字|かんじ]` 형식으로 출력한다. 표기는 한자에만 단다(가나·한글에는 달지 않는다). 첫 마디(`scenarios.ts`)와 단어 데이터에는 모든 레벨에 이미 표기가 있다.
  - 가타카나: AI에게 요청하지 않는다. 화면에 그릴 때 코드가 가타카나 묶음(장음 `ー` 포함)을 같은 소리의 히라가나로 바꿔 단다(`コーヒー` → こーひー). 한자 표기의 본문·읽기 안에 있는 가타카나와 `・`는 건드리지 않는다. 따로 쓰인 `ヵ`·`ヶ`(`3ヶ月`)에는 읽기를 달지 않는다. か·が·こ로 읽어서 같은 소리의 히라가나(ゕ·ゖ)가 읽기가 되지 않기 때문이다. 음성 SSML(`audio.md`)은 지금처럼 한자 표기만 쓴다. 바꾸면 이미 만든 단어·예문 음성의 SSML이 달라져 전체를 다시 만들어야 한다.
  - AI 출력을 HTML로 넣지 않는다.
  - 여는 괄호만 빠진 표기(`[風邪|かぜ]気味|ぎみ]`의 `気味|ぎみ]`, 2026-10-17 운영에서 나옴)는 `|` 바로 앞의 한자 묶음을 본문으로 보고 읽기를 단다. `|` 바로 앞에 한자가 없으면(`コーヒー|こーひー]`) 본문에 한자가 없는 표기처럼 `|`부터 `]`까지의 읽기를 버린다. `|`가 빠진 표기(`お願[ねが]い`, 2026-10-20 종료 피드백 예문에서 나옴)는 `[` 바로 앞의 한자 묶음을 본문으로, 괄호 안 히라가나를 읽기로 본다. `[` 앞이 한자가 아니거나 괄호 안이 히라가나만이 아니면(`[漢字]`) 아래 규칙을 따른다. 그 밖의 깨진 표기(닫는 괄호나 `|`가 빠진 것)는 읽기가 어디서 끝나는지 알 수 없어 괄호 기호만 지우고 일반 텍스트로 보여 준다. `|`가 두 개인 표기(`[漢字|かん|じ]`)와 `|` 바로 앞이 다른 표기의 `]`인 것(`[風邪|かぜ]|ぎみ]`)도 여는 괄호만 빠진 표기로 보지 않고 이 규칙을 따른다(2026-10-18 구현 때 정함. 앞 경우는 기존 테스트가 정한 동작이고, 둘 다 운영에서 나온 적이 없다).
  - 본문에 한자가 없는 표기(`[コーヒー|こーひー]`, 한글 이름 등)는 AI가 단 읽기를 버리고 본문만 남긴다. 그 본문의 가타카나에는 위 규칙대로 코드가 읽기를 단다.
  - 종료 피드백(잘한 점, 고칠 점의 설명·예문)은 일본어를 쓸 때 모든 한자에 표기를 달게 요청한다. 턴 교정의 설명(`explanation_ko`)은 표기를 요청하지 않지만 모델이 교정 문장의 표기를 따라 쓸 수 있으므로 같은 규칙으로 그린다.
- **프롬프트 인젝션**: 시스템 프롬프트로 역할을 유지하게 하고, 출력은 스키마로 강제한다. 남용 비용의 상한은 300자, 20턴, 일일 한도가 정한다.

  - っ는 앞 글자의 ㅅ받침으로만 쓰고 따로 음절을 만들지 않는다: 学校 → 갓코-, 行って → 잇테, 間に合った → 마니앗타. 큰 つ는 받침으로 줄이지 않고 츠로 쓴다: 発言 → 하츠겐

## 문장 뜯어보기 (2026-10-17 추가)
- **목적**: 번역과 교정 설명은 문장 전체를 한 번에 옮겨서, 문장의 어느 부분이 어떤 뜻인지 알 수 없다(2026-10-17 운영 확인에서 사용자가 지적). 문장을 의미 조각(단어·조사 묶음·서술어)으로 나눠 조각마다 한국어 뜻을 보여 준다.
- **대상과 위치**: 모든 언어·레벨. 대화의 AI 말풍선(첫 마디 포함)과 교정 카드의 고친 문장에 둔다. 종료 피드백, 단어, 레벨업 테스트에는 두지 않는다. 처음에는 닫혀 있고 [문장 뜯어보기]를 눌러 열고 닫는다. 배치는 `ui.md`를 따른다.
- **형식**: `[{ text, meaning_ko }]`. `text`는 문장에 나온 그대로의 조각이고, `meaning_ko`는 그 조각의 문장 속 뜻을 짧게 쓴 한국어다. 일본어 조각의 읽기 표기는 AI에게 요청하지 않는다. 검사를 통과하면 코드가 AI가 준 글자 대신 원래 문장(표기 포함)을 조각 경계에서 잘라 `text`로 저장한다. 그래서 타일의 읽기·대소문자·문장부호는 늘 말풍선·교정 문장과 같고 출력 토큰도 줄어든다. 조각 사이의 공백·문장부호는 앞 조각에 붙이고, 여는 괄호·따옴표(`「`, `(`, `“`)와 통화 기호(`$`)는 뒤 조각에 붙인다(`[彼|かれ]は` / `「[行|い]く」と`). 문장 맨 앞의 것은 첫 조각에 붙는다. 문장에 깨진 표기가 있으면 `parseFurigana`가 읽은 모양(화면에 보이는 모양)으로 다시 써서 자른다. 표기 하나가 두 조각에 걸치면 검사 실패로 본다. 조각은 문장 순서대로다. 조사·어미는 앞말과 묶는다(`[家|いえ]で` 집에서, `[休|やす]んでいました` 쉬고 있었어요. 영어는 `at home` 집에서).
- **만드는 곳**: 대화는 턴마다 Claude가 `reply_breakdown`·`correction.breakdown`을 함께 만든다(ADR-018). 첫 마디는 `scenarios.ts`의 `breakdown`이며 첫 마디·한글 발음처럼 AI로 초안을 만들고 사람이 검수한다.
- **검사**(`lib/breakdown`): 조각의 `text`를 순서대로 이어 붙인 것과 원래 문장을 비교한다. 둘 다 후리가나 표기를 지우고(`stripFurigana`), 공백·문장부호·기호(`\p{S}`)를 빼고, 영어는 대소문자를 무시한다. 공백·문장부호만 있는 조각(`?`)은 문장에서 자를 자리가 없으므로 빼고 검사한다. 그 글자는 위 규칙대로 이웃 조각에 붙는다. 모델이 끝 문장부호를 따로 조각으로 만들어도 뜯어보기 전체가 사라지지 않게 하려는 것이다(프롬프트에도 그런 조각을 만들지 말라고 쓴다). 같지 않거나, 남은 조각이 없거나, 남은 조각에 `meaning_ko`가 빈 것이 있으면 그 문장의 뜯어보기를 `null`로 저장해 버튼을 숨긴다. 턴은 성공으로 처리한다. 모델이 조각을 빼먹거나, 사전형으로 바꾸거나(`食べたり` → `食べる`), 한자를 가나로 바꾸면 대응이 틀려지기 때문이다. 첫 마디의 `breakdown`은 단위 테스트가 같은 검사로 확인한다.
  - 검사에 맞지 않으면 `console.warn`으로 `{ ai: "breakdown_invalid", target: "reply" | "corrected", language, level }` 한 줄을 남긴다(문장·조각 내용은 남기지 않는다). 통과율이 낮아 기능이 조용히 사라지는 것을 운영 로그로 알기 위해서다.
  - 구현 뒤 실제 턴 약 30개(언어·레벨 섞어서)로 검사 통과율, 응답 시간, 입출력 토큰을 재서 `usage.md`의 추정을 고친다. 통과율이 낮으면 프롬프트를 고친다. 유료 API 호출이므로 하네스 step 안에서 하지 않고 phase가 끝난 뒤 메인 세션에서 한다.
- **저장**: `chat_turns.reply_breakdown`(jsonb)과 `correction` jsonb 안의 `breakdown`. 기능을 넣기 전의 턴과 검사에 맞지 않은 문장은 없다(`null`·키 없음).
- 뜯어보기는 대화 기록으로 Claude에 다시 보내지 않는다(기록에는 reply만 넣는다). 새 턴 알림 영역(`aria-live`)에도 넣지 않는다.

## 배운 단어 써 보기 (2026-10-19 추가)
- **목적**: 카드로 본 단어를 대화에서 직접 말해 보게 해서 오래 기억하게 하고, 단어 학습과 대화를 하루 학습 하나로 잇는다(ADR-023). 기능 전에는 대화가 사용자가 배운 단어를 몰랐다.
- **흐름 예**: 일본어 입문 사용자가 오늘 `犬, 猫, 美味しい, とても, 少し, 一緒に, 買う, 話す, 聞く, 読む`를 배우고 "카페에서 음료 주문하기"에 들어간다. 첫 마디(고정)에 답하면 AI가 상황에 맞는 `美味しい · とても · 少し · 一緒に`를 고르고, 대화방 위에 "오늘 단어 0/4" 줄이 나타난다. 점원이 "ケーキもありますよ。どうしますか？"처럼 一緒に를 쓰기 쉬운 질문을 하고, 사용자가 "ケーキも一緒にください。"라고 하면 一緒に에 체크가 된다. 犬·猫·読む는 이 대화에서 빠지고, 같은 날 "좋아하는 것 이야기하기"에서는 후보 앞쪽에 와서 다시 고를 수 있다.
- **후보 단어**: 예약 RPC(`begin_chat_turn`)가 계정 잠금 안에서 DB 시각으로 정한다. 이번 턴이 세션의 첫 턴(`turn_no = 1`)이고 세션에 목표 단어가 아직 없을 때만 돌려준다.
  - 세션 언어의 단어 중 이 사용자의 `user_words.first_seen_at`이 오늘(한국 날짜)인 단어다(출처 `today`). 없으면 한국 날짜로 오늘을 포함한 7일 안인 단어다(출처 `recent`). 그것도 없으면(첫날 등) 후보가 없다. 단어의 레벨과 `status`(known/review)는 따지지 않는다.
  - 순서: 오늘 이 계정의 대화에서 이미 쓴 단어(오늘 만든 `done` 턴들의 `used_word_ids`, 모든 세션)를 뒤로 보내고, 그 안에서는 `first_seen_at`이 최근인 것부터, 같으면 단어 `id` 순이다. 앞에서 **20개**까지만 준다. Pro는 하루 30개를 배울 수 있어 다 넣으면 프롬프트가 길어진다.
  - 후보마다 오늘 대화에서 이미 썼는지(`used_today`)를 함께 돌려준다. Free는 하루 10개라 후보가 20개를 넘지 않아 순서만으로는 고르기에 영향이 없으므로, 고르기 지시에 표시로 넘긴다.
- **고르기**(첫 턴): 후보에 1부터 번호를 붙여 `번호. 단어(읽기) — 뜻`으로 시스템 프롬프트에 넣는다(읽기는 일본어에서 단어와 다를 때만). 오늘 이미 쓴 후보는 끝에 `(오늘 씀)`을 붙인다. AI는 이 상황과 역할에서 자연스럽게 나올 단어만 **최대 5개** 골라 `target_words`(번호 배열)로 준다. 맞는 단어 중에서는 `(오늘 씀)`이 없는 단어를 먼저 고른다. 화제를 바꿔야 쓸 수 있는 단어는 고르지 않고, 맞는 단어가 없으면 빈 배열이다. 이 턴의 응답부터 고른 단어를 유도한다.
  - 프롬프트는 "학습자가 대답에 쓸 수 있는 단어"를 고르게 하고, 고를 것과 고르지 않을 것의 예(카페 주문이면 '맛있다·조금·같이'는 고르고 '개·고양이'는 고르지 않는다)를 넣고, "맞는 단어가 하나도 없을 때만 빈 배열"이라고 쓴다. 2026-10-20 실측에서 "자연스럽게 나올 단어만"이라고만 쓰자 카페 주문에서도 하나도 고르지 않았다(effort low라 생각 없이 빈 배열을 골랐다).
  - 고른 단어는 세션의 목표 단어가 된다. 첫 턴이 확정될 때만 저장하고 그 뒤에는 바꾸지 않는다. 첫 턴이 실패하면(503·처리 기한 만료) 다음 첫 턴 요청에서 다시 고른다.
  - 후보가 없거나 AI가 하나도 고르지 않으면 목표 단어가 없다. 이 세션에는 줄이 없고 평소처럼 대화한다.
  - 세션을 만들 때 고르지 않는 이유(ADR-023): 첫 마디가 고정이라 그때는 Claude를 부르지 않는다. 부르면 입장이 느려지고, 턴으로 세지 않는 AI 호출이 생겨 세션을 여러 번 만들면 한도 없이 AI를 부를 수 있다. 그래서 첫 마디 화면에는 줄이 없고 첫 답장부터 나타난다.
  - 첫 턴이 이미 끝난 세션(기능을 넣기 전에 대화를 시작한 세션 포함)은 목표 단어가 없다. 기능을 넣기 전에 만들었어도 턴이 없는 세션은 첫 턴에 고른다(세션 생성 시각으로 막지 않는다).
- **유도**(목표 단어가 있는 턴): 시스템 프롬프트에 목표 단어를 1부터 번호를 붙여 `번호. 단어(읽기) — 뜻 — 썼음/아직`으로 넣는다(첫 턴은 위 후보 목록과 고르기 지시로 대신한다). 대화 기록에는 넣지 않는다(기록에는 reply만 넣는다).
  - AI는 역할을 지키면서, 아직 쓰지 않은 목표 단어를 학습자가 대답에 쓰기 쉬운 질문이나 상황을 만든다. 한 응답에서 한 단어만 노린다.
  - 아직 쓰지 않은 목표 단어를 AI가 `reply`에서 먼저 말하지 않는다. 따라 하지 않고 떠올려 말하게 하려는 것이다. 막히면 사용자는 대화방 위의 줄에서 단어와 뜻을 본다.
  - 교정(`correction.corrected`)은 이 규칙을 따르지 않는다. 교정은 자연스럽고 맞는 문장이 먼저라 목표 단어가 들어갈 수 있다(특히 한국어 입력의 "이렇게 말하면 돼요").
  - 프롬프트의 `썼음/아직`은 앞 턴까지의 상태다. 사용자가 이번 말에서 쓴 목표 단어는 `아직`이어도 쓴 것으로 보고 reply에서 받아 말해도 된다고 지시한다(2026-10-20 phase 뒤 spec 대조에서 더함). 그러지 않으면 AI가 사용자가 막 쓴 단어를 받아 말하기를 피하거나, 마지막 단어를 쓴 턴에도 한 번 더 유도할 수 있다.
  - 역할을 벗어나 "이 단어를 써 보세요"라고 말하지 않는다.
  - 상황 목표가 먼저다. 단어를 쓰게 하려고 화제를 바꾸거나 대화를 억지로 늘리지 않는다. 모두 썼으면 더 유도하지 않는다. 난이도는 "레벨별 조절"을 따른다.
- **쓴 단어 판단**: 목표 단어를 고르는 턴과 목표 단어가 있는 턴마다 `used_words`(번호 배열)를 받는다. 이번 입력에서 학습자가 학습 언어로 직접 쓴 목표 단어다(첫 턴은 후보 번호이고, 고른 단어만 해당한다).
  - 활용형(`買う` → `買いました`, `decide` → `decided`)과 다른 표기(`美味しい` → `おいしい`)도 쓴 것으로 본다. 문자열 비교로는 이것을 가릴 수 없어 AI가 판단한다.
  - 한국어로 쓴 것은 치지 않는다. "이렇게 말하면 돼요"로 받은 문장은 직접 말한 것이 아니다. 그 문장을 보고 다음 턴에 학습 언어로 직접 쓰면 친다(직접 입력해 말해 본 것이다).
  - 문법이 틀려도 그 단어를 썼으면 친다. 고치는 것은 교정이 한다.
- **검사**(`lib/targetWords`): 번호를 단어 `id`로 바꾼다. 정수가 아니거나 범위 밖인 번호와 중복은 버린다. 목표 단어는 앞에서 5개까지만 남기고, 쓴 단어는 목표 단어 안의 것만 남긴다. 맞지 않는 값은 실패로 보지 않고 버리며 턴은 성공으로 처리한다. 숫자가 아닌 값(문자열 등)은 다른 필드처럼 스키마가 막는다(구조화 출력이 타입을 강제하므로 나오지 않는다. 나오면 `invalid_output`).
- **저장**: `chat_sessions.target_word_ids`(text[], 고른 순서)와 `target_source`(`today`/`recent`), `chat_turns.used_word_ids`(text[], 그 턴에 쓴 목표 단어). 세션에서 쓴 단어는 `done` 턴들의 합집합이다. 목표 단어가 없는 세션과 턴은 `null`이다.
  - `finish_chat_turn`은 `p_target_word_ids text[] default null`, `p_target_source text default null`, `p_used_word_ids text[] default null`을 받는다. 세션에 목표 단어가 없고 이 턴이 첫 턴일 때만 목표 단어를 저장한다. 그 사용자의 `user_words`에 있고 세션 언어인 단어만 저장하고(남지 않으면 목표 단어 없음), 쓴 단어는 저장된 목표 단어 안의 것만 저장한다.
  - 성공 응답에 세션의 목표 단어 상태를 돌려준다(아래 "응답").
- **응답**: 메시지 응답과 대화방 읽기에 `targetWords: [{ id, word, reading, meaningKo, used }] | null`(목표 단어 순서)과 `targetSource`를 담는다. 화면은 메시지 응답으로 줄을 바로 갱신하고, 턴 확정 뒤의 다시 읽기(`journey.md` "예외 흐름"의 뒤로 가기)를 기다리지 않는다.
- **화면**(`ui.md`): 대화방 상단의 단어 줄, 종료 피드백의 결과 카드, 단어 회차 결과의 [대화하러 가기]. 줄과 카드의 이름은 출처가 `today`면 "오늘 단어", `recent`면 "최근 단어"다.
- **비용**(`usage.md`, 2026-10-20 `count_tokens` 실측): 목표 단어가 있는 턴(4개)은 입력이 약 570토큰, 후보 10개를 주는 첫 턴은 약 910토큰 늘고, 출력은 번호 몇 개다. 한국어 지시문이 토큰을 많이 먹어서, 처음 문구(+894·+1,244)를 줄였다.
- **확인**: 구현 뒤 실제 대화 몇 개(언어·레벨·출처를 섞어서)로 고른 단어가 상황에 맞는지, 유도가 억지스럽지 않은지, AI가 목표 단어를 먼저 말하지 않는지, 쓴 단어 판단이 맞는지, 늘어난 토큰을 본다. 유료 API 호출이므로 하네스 step 안에서 하지 않고 phase가 끝난 뒤 메인 세션에서 한다.
  - 2026-10-20 로컬 실측(대화 3개, 15턴: 일본어 입문 카페·초보 편의점(같은 날 두 번째), 영어 중급 옷 가게(최근 단어)): 3~5개를 골랐고 오늘 쓴 단어는 뺐다. 유도는 역할 안에서 자연스러웠고(커피 진하기 → 少し, 집에 있는 재킷 → already), 주문이 끝나면 더 끌지 않았다. 쓴 단어 판단은 활용형(買った·decided), 가나 표기(おいしい), 한 턴 두 단어, 교정 문장 따라 쓰기가 모두 맞았고 한국어 입력은 치지 않았다. AI가 아직 쓰지 않은 목표 단어를 먼저 말한 경우가 1번 있었다(とてもおいしいですよ). 응답은 2~7초였다.
- **지표**: 새 이벤트는 두지 않는다. 쓴 단어가 DB에 남으므로 나중에 이 기능이 단어 기억(오답 복습·레벨업 정답률)에 도움이 됐는지 따로 볼 수 있다.

## 세션 종료 피드백
- **시작 RPC**: `profiles → chat_sessions` 순서로 잠그고 만료 작업을 복구한다. 살아 있는 메시지 작업이 있으면 409, 이미 `ending`이면 202, `ended`이면 저장된 결과를 반환한다.
- `active`이고 성공한 턴이 있으면 `ending`, `feedback_status = pending`으로 전환하고 새 UUID 토큰과 90초 기한을 예약한다. 잠금을 해제한 뒤 예약을 얻은 요청만 Claude로 피드백(아래 "피드백 형식")을 생성한다.
- **피드백 형식**(2026-10-20 바꿈, ADR-025): `{ good: string, improve: [{ point: string, example: string }] }`. 일본어 입문~중급은 고칠 점마다 `example_pron_ko`(example의 한글 발음)를 더 받는다. 그 밖의 언어·레벨은 요청하지 않고 키도 없다.
  - `good`은 잘한 점을 한국어 해요체 1~2문장으로 쓴다. `point`는 고칠 점을 한국어 해요체로 짧게 설명한다(사용자가 한 말을 인용할 수 있다). 학습 언어는 `good`·`point`에서 짧은 인용에만 쓰고 문장 전체를 학습 언어로 쓰지 않는다(2026-10-20 실측: 프롬프트의 `good`·`point` 정의에 "한국어"가 없을 때 일본어 피드백 8개 중 3개가 `good`·`point`를 일본어로 썼다). `example`은 더 나은 학습 언어 표현 한 문장이고, `point`에 예문을 되풀이하지 않는다. 일본어는 `good`·`point`의 인용과 `example`의 모든 한자에 `[漢字|かんじ]` 표기를 단다. 발음은 위 "한글 발음"의 표기 규칙(`PRONUNCIATION_RULES`)을 따른다.
  - **검사**(`client.ts`): `point`가 공백뿐인 항목은 버리고 남은 항목을 앞에서 3개까지 저장한다. `example`이 공백뿐이면 빈 문자열로 저장하고 화면은 예문 줄 없이 설명만 그린다. 발음이 비었거나 검사(`lib/pronunciation`)에 맞지 않으면 그 발음만 `null`로 저장해 숨기고 피드백은 성공으로 처리한다. 프롬프트에도 `point`를 비우지 말고, 예문은 학습 언어 한 문장으로, 발음은 표기 규칙대로 한글로만 쓰라고 쓴다.
  - **옛 형식**: 2026-10-20 전에 만든 피드백은 `improve`가 문자열 배열이다(설명과 예문이 한 문장에 섞여 있다). 마이그레이션하지 않고(`feedback`은 형식 검사 없는 jsonb다), 읽을 때 문자열 항목은 전처럼 한 줄로 그린다.
  - 처음에는 `improve`를 문자열로 받아 예문이 설명 속에 섞여 있었고 발음을 붙일 자리가 없었다. 예문을 따로 받으면 모든 언어에서 예문이 한 줄로 눈에 띄고, 일본어 입문~중급은 그 아래에 발음을 둘 수 있다.
- **완료 RPC**: 자신의 토큰·기한을 확인한 뒤 피드백 저장, `feedback_status = ready`, `status = ended`, `ended_at` 기록, 토큰 해제를 한 트랜잭션으로 처리한다.
- **생성 실패 또는 처리 기한 만료**: `feedback_status = fallback`, `status = ended`, `ended_at`과 고정 대체 결과를 함께 저장하고 토큰을 해제한다. 대체 결과는 `feedback = { message: "대화 기록은 저장됐어요. 종합 피드백을 만들지 못했으니 대화 아래의 교정을 확인해 주세요." }`이며, 실제 학습 평가처럼 꾸미지 않는다. 실패 확정과 `chat_failed` 기록은 한 번만 일어난다.
- 오늘 실패가 10회 이상이어도 종료는 가능하다. 이때는 Claude 호출 없이 같은 대체 결과로 끝내며 새 AI 실패로 세지 않는다. 이 기준은 새 AI 호출의 차단 기준이다. 다른 세션에서 이미 시작한 작업이 실패하면 당일 실패 기록은 10회를 넘을 수 있다.
- 종료 응답이 유실되거나 DB 저장 전에 서버가 중단돼도 다음 `/end`가 저장 결과 또는 기한 만료 복구 결과를 반환한다. 기한 내 DB 저장을 재시도할 때에도 AI 호출부터 반복하지 않는다. 대체 결과가 확정된 세션의 종합 피드백을 다시 생성하는 기능은 MVP에서 제외한다.
- 목표 단어가 있는 세션이면 피드백 화면에 쓴 단어 결과 카드("오늘 단어 4개 중 3개를 썼어요" + 단어 목록)를 둔다(`ui.md` "화면별 구성"). 저장된 목표 단어와 쓴 단어로 그리며 Claude에 요청하지 않는다. 대체 결과(fallback)에서도 보여 준다.
- AI가 레벨 조정을 제안하지는 않는다. 피드백은 잘한 점과 고칠 점만 준다. 레벨을 올리려면 홈의 레벨업 테스트로, 내리려면 홈에서 직접 바꾼다.

## 모델
환경변수 `CLAUDE_MODEL`로 바꿀 수 있고, 기본값은 `claude-sonnet-5-5`다. 2026-10-08 일본어 샘플 비교에서 Haiku 4.5는 후리가나 누락과 교정 누락이 잦아 바꿨다(ADR-012). `output_config.effort`를 받지 않는 모델(Haiku 4.5 등)로 바꾸면 모든 호출이 API 오류가 된다.
