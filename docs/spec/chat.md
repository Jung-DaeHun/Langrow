# AI 대화

## 상황 목록
- 코드 상수(`src/lib/scenarios.ts`)로 둔다. 레벨당 4개, 총 20개이며 영어와 일본어가 같은 목록을 쓴다.
- 상황마다 `id / 제목 / 사용자 목표`는 공통으로, `AI 역할·배경 / 첫 마디`는 en과 ja 각각 정의한다.
  - 첫 마디에는 한국어 번역을 붙이고, 일본어는 후리가나 표기를 포함한다. 일본어 입문~중급 상황(레벨 1~3)의 첫 마디에는 한글 발음(`pronKo`, 아래 "한글 발음")도 붙인다. 상황은 그 레벨의 대화방에만 나오므로 상급·고수 첫 마디의 발음은 보일 일이 없어 두지 않는다.
  - 초안은 AI로 만들어도 되지만, 사람이 검수한 뒤 코드에 넣는다.
- 문화적 배경은 언어별 데이터에서 사람이 정한다 (예: 영어는 미국 카페, 일본어는 편의점). 첫 마디가 이미 배경을 정하므로 AI가 바꾸지 않는다.

## 대화 진행
1. 현재 레벨의 상황을 고르면 세션을 만들고 **고정된 첫 마디**를 보여 준다.
   - 이때 Claude를 부르지 않는다. 다른 레벨의 상황이면 400을 돌려준다.
2. 사용자 발화마다 Claude로 응답 하나를 생성하고 아래 구조로 받는다 (zod로 검증). 실패 시 재시도는 `backend.md` "Claude 연동"의 최대 1번 규칙을 따른다.
   ```
   { reply: string,                 // AI의 다음 대사
     reply_ko: string,              // reply의 한국어 번역
     correction: { corrected: string, explanation_ko: string } | null }
   ```
   - 일본어 입문~중급은 `reply_pron_ko`(reply의 한글 발음)와 `correction.corrected_pron_ko`(corrected의 한글 발음)를 더 받는다(아래 "한글 발음"). 그 밖의 언어·레벨은 요청하지 않는다. 그 턴의 `reply_pron_ko`는 `null`로 저장되고 `correction`에는 `corrected_pron_ko` 키가 없다(읽을 때 없는 키는 발음 없음으로 본다).
   - 모든 언어·레벨에서 `reply_breakdown`(reply의 조각 뜻)과 `correction.breakdown`(corrected의 조각 뜻)을 더 받는다(아래 "문장 뜯어보기").
3. 교정은 사용자 메시지 바로 아래에 보여 준다. 틀린 게 없으면(`null`) 보여 주지 않는다.
4. 모든 레벨에서 한국어로 입력해도 된다. 그러면 교정란에 "이렇게 말하면 돼요"가 나온다. 처음에는 입문·초보만 허용했는데, 2026-10-17 운영에서 상급 사용자가 한국어로 입력했을 때 바꾼 문장이 나오지 않아 모든 레벨로 넓혔다(ADR-016). 말이 막힐 때 한국어로 쓰고 바로 배우는 흐름은 레벨과 상관없이 필요하다.
   - 입력에 한국어가 들어 있으면 `correction`은 `null`이 아니다. 한국어 문장이 자연스러워도 마찬가지다. `corrected`는 사용자의 말을 학습 언어로 옮긴 문장이고, `explanation_ko`는 핵심 표현을 짧게 설명한다.
   - 한국어 문장 자체의 맞춤법·표현은 고치거나 평가하지 않는다.
   - 한국 사람 이름·지명은 일본어에서는 가타카나(정대훈 → チョン・デフン), 영어에서는 로마자로 쓴다. 한글을 학습 언어 문장에 섞지 않는다.
5. **한 세션은 최대 20턴이다.** 20번째 응답에 `turnsLeft: 0`이 담겨 오면, 클라이언트가 이어서 `/end`를 호출한다. 대화 응답과 피드백을 한 요청에서 처리하지 않는다.
6. **`/end`는 멱등이다.** 세션 상태는 `active → ending → ended`로 이동한다.
   - 종료 처리 중에는 새 메시지를 받지 않는다. 유효한 턴이 처리 중이면 종료 요청을 409로 거부한다.
   - 이미 `ending`이면 Claude를 다시 부르지 않고 `202 { status: 'ending', retryAfterSeconds: 2 }`를 반환한다. 클라이언트는 화면이 보이는 동안 간격을 두고 `/end`를 재호출하고, 화면에 돌아오면 재개한다.
   - `ended`이면 저장된 피드백과 `feedback_status`를 그대로 반환한다. 처리 실패도 고정 대체 결과로 종료하므로 다음 요청에서 복구할 수 있다.
   - 성공한 턴이 0개인 세션은 Claude를 부르지 않고 `ended`, `feedback_status = skipped`로 끝낸다.
7. **입력은 1~300자다.** 앞뒤 공백을 제거한 뒤 센다. 클라이언트와 서버가 같은 함수(`lib/text`)로 센다.
8. 스트리밍 없이 응답을 한 번에 받는다.
9. **IME 처리**: 조합 중(`isComposing`)일 때 누른 Enter로는 전송하지 않는다. 한글·일본어 입력이 반쯤 전송되는 버그를 막기 위해서다.
10. **음성**: AI 말풍선(첫 마디 포함)과 교정의 고친 문장은 브라우저 음성으로 들을 수 있다. 학습 언어 음성이 없는 기기에서는 버튼을 숨긴다(`audio.md`).

## 대화 1턴 처리 (트랜잭션으로 예약 → AI 호출 → 결과 확정)

한 턴은 `chat_turns`의 한 행이다. 동일 세션의 진행 중인 작업은 하나만 허용한다.

1. 로그인·동의·온보딩 상태와 입력을 확인한다. 세션을 `id + user_id`로 조회하며 없거나 남의 세션이면 404다. 세션에 저장된 언어·레벨로 이어서 대화한다.
2. **예약 RPC**: `profiles` 행을 잠근 뒤 해당 사용자의 만료된 작업을 복구하고 대상 세션을 잠근다. 아래 검사와 예약을 하나의 짧은 트랜잭션에서 처리한다.
   - `status != active`이거나 유효한 `operation_token`이 있으면 409다. `unique(session_id, turn_no)`만으로 실행을 잠그지 않는다.
   - 오늘 `chat_failed`가 10개 이상이면 `429 AI_FAILURE_LIMIT`다.
   - 성공한 세션 턴이 이미 20개면 `409 SESSION_FULL`이다.
   - 오늘 계정의 `pending + done` 턴이 플랜 한도에 도달했으면 예약 없이 `limit_reached`를 기록하고 `429 LIMIT_REACHED`를 반환한다.
   - `turn_no = 마지막 done 턴 + 1`로 `pending`을 생성한다. 그 행의 UUID를 세션 `operation_token`으로 저장하고 `operation_expires_at = DB 현재 시각 + 90초`로 둔다. 커밋 후에도 pending 예약은 한도에 포함된다.
3. **Claude 호출**: DB 잠금을 해제한 뒤 시스템 프롬프트 + 첫 마디 + 순서대로 정렬한 `done` 턴들 + 이번 입력을 보낸다.
4. **성공 확정 RPC**: 같은 잠금 순서로 `active` 상태, 요청의 토큰 일치, 기한 내 처리, 해당 pending 행을 확인한다. 응답 저장·`done` 전환·토큰 해제·활동일/연속일 갱신을 함께 커밋하고 `turnsLeft`를 반환한다. 오늘 예약된 done 턴 수가 한도에 도달하면 같은 트랜잭션에서 `limit_reached`도 기록한다.
5. **실패 확정 RPC**: 해당 작업을 아직 소유한 경우에만 pending 삭제·예약 반환·토큰 해제·`chat_failed` 기록을 함께 커밋한 뒤 `503 AI_UNAVAILABLE`을 반환한다. 재시도까지 실패한 작업당 한 번만 기록하며, `props`에 `operation_token`, `kind(turn/feedback)`, 실패 사유를 넣는다.
6. 이미 복구됐거나 기한이 지난 토큰으로 온 결과는 저장하지 않고 409로 처리한다. 늦은 성공/실패 응답이 새 작업을 변경하거나 같은 실패를 다시 기록해서는 안 된다.

## 처리 중단 복구
- 대화 세션 생성·메시지·종료 API의 쓰기 RPC는 `profiles` 잠금을 잡은 뒤 해당 계정의 만료된 작업을 복구한다. 성공/실패 확정 RPC도 자신의 작업이 만료됐으면 같은 복구 규칙을 적용한다.
- `active`의 만료된 작업: 해당 토큰의 pending 행만 삭제하고 토큰을 해제한다. 실패 이벤트는 한 번 기록하며 사용자는 다시 전송할 수 있다.
- `ending`의 만료된 작업: 아래 고정 대체 피드백으로 `ended`를 확정한다. AI를 다시 호출하지 않는다.
- 기한은 AI 요청 전체 예산(최대 약 40초)과 라우트 실행 상한(60초)보다 긴 90초다. 예약·판정 시각은 DB 기준이며, 복구 뒤 도착한 결과는 토큰으로 차단한다.
- 정리용 cron은 두지 않는다. 아직 처리 기한이 남은 작업은 409/202로 안내하고 만료 뒤 다음 API 요청에서 복구한다. 클라이언트는 표시된 남은 사용량으로 입력을 막지 않고, 서버의 `429` 응답 뒤에만 막는다. 만료된 pending이 표시 사용량에 포함돼 있어도 실제 한도는 서버의 복구 후 판정에 따른다.
- 사용자가 끝내지 않은 유휴 `active` 세션은 자동으로 종료하지 않는다 (`ending` 작업의 만료 복구만 한다).
- 네트워크가 끊긴 뒤 이미 성공한 메시지를 사용자가 다시 전송하는 중복은 MVP에서 감수한다. 메시지 멱등 키는 도입하지 않는다.

## 레벨별 조절
시스템 프롬프트에 레벨 지침을 넣는다.

| 레벨 | AI 문장 | 교정 강도 | 번역 | 일본어 후리가나 | 일본어 한글 발음 |
|---|---|---|---|---|---|
| 입문 | 아주 짧고 쉬운 표현 | 의미가 안 통하는 오류만 | 기본 표시 | 모든 한자·가타카나 | 기본 표시 |
| 초보 | 짧은 문장 | 주요 문법 | 기본 표시 | 모든 한자·가타카나 | 기본 표시 |
| 중급 | 일상 수준 | 문법 + 어색한 표현 | 눌러서 보기 | 모든 한자·가타카나 | 번역과 함께 눌러서 보기 |
| 상급 | 자연스러운 속도 | 뉘앙스까지 | 눌러서 보기 | 모든 한자·가타카나 | 없음 |
| 고수 | 원어민 수준, 관용구 | 뉘앙스·격식까지 | 눌러서 보기 | 모든 한자·가타카나 | 없음 |

- **후리가나**: 일본어는 모든 레벨에서 한자와 가타카나 위에 히라가나 읽기를 단다. 대화(첫 마디·말풍선·교정·종료 피드백), 단어(카드·빈칸 문장·보기·AI 해설), 레벨업 테스트 모두 같다. 가나 익히기 카드에는 달지 않는다(글자를 익히는 연습이라서). 처음에는 입문~중급의 한자에만 달았는데, 2026-10-17 모든 레벨과 가타카나로 넓혔다(ADR-016). 프론트에서 `<ruby>` React 요소로 그린다.
  - 한자: AI가 `[漢字|かんじ]` 형식으로 출력한다. 표기는 한자에만 단다(가나·한글에는 달지 않는다). 첫 마디(`scenarios.ts`)와 단어 데이터에는 모든 레벨에 이미 표기가 있다.
  - 가타카나: AI에게 요청하지 않는다. 화면에 그릴 때 코드가 가타카나 묶음(장음 `ー` 포함)을 같은 소리의 히라가나로 바꿔 단다(`コーヒー` → こーひー). 한자 표기의 본문·읽기 안에 있는 가타카나와 `・`는 건드리지 않는다. 따로 쓰인 `ヵ`·`ヶ`(`3ヶ月`)에는 읽기를 달지 않는다. か·が·こ로 읽어서 같은 소리의 히라가나(ゕ·ゖ)가 읽기가 되지 않기 때문이다. 음성 SSML(`audio.md`)은 지금처럼 한자 표기만 쓴다. 바꾸면 이미 만든 단어·예문 음성의 SSML이 달라져 전체를 다시 만들어야 한다.
  - AI 출력을 HTML로 넣지 않는다.
  - 여는 괄호만 빠진 표기(`[風邪|かぜ]気味|ぎみ]`의 `気味|ぎみ]`, 2026-10-17 운영에서 나옴)는 `|` 바로 앞의 한자 묶음을 본문으로 보고 읽기를 단다. `|` 바로 앞에 한자가 없으면(`コーヒー|こーひー]`) 본문에 한자가 없는 표기처럼 `|`부터 `]`까지의 읽기를 버린다. 그 밖의 깨진 표기(닫는 괄호나 `|`가 빠진 것)는 읽기가 어디서 끝나는지 알 수 없어 괄호 기호만 지우고 일반 텍스트로 보여 준다. `|`가 두 개인 표기(`[漢字|かん|じ]`)와 `|` 바로 앞이 다른 표기의 `]`인 것(`[風邪|かぜ]|ぎみ]`)도 여는 괄호만 빠진 표기로 보지 않고 이 규칙을 따른다(2026-10-18 구현 때 정함. 앞 경우는 기존 테스트가 정한 동작이고, 둘 다 운영에서 나온 적이 없다).
  - 본문에 한자가 없는 표기(`[コーヒー|こーひー]`, 한글 이름 등)는 AI가 단 읽기를 버리고 본문만 남긴다. 그 본문의 가타카나에는 위 규칙대로 코드가 읽기를 단다.
  - 종료 피드백(잘한 점·고칠 점)은 일본어를 인용할 때 모든 한자에 표기를 달게 요청한다. 턴 교정의 설명(`explanation_ko`)은 표기를 요청하지 않지만 모델이 교정 문장의 표기를 따라 쓸 수 있으므로 같은 규칙으로 그린다.
- **프롬프트 인젝션**: 시스템 프롬프트로 역할을 유지하게 하고, 출력은 스키마로 강제한다. 남용 비용의 상한은 300자, 20턴, 일일 한도가 정한다.

## 한글 발음 (2026-10-14 추가)
- **목적**: 가나를 아직 다 읽지 못하는 입문자가 일본어 문장을 소리 내어 읽게 한다. 한자의 읽기는 후리가나가, 문장 전체의 소리는 한글 발음이 보여 준다.
- **대상과 위치**: 일본어 입문~중급(`showsPronunciation`. 2026-10-17 후리가나를 모든 레벨로 넓힐 때 발음은 넓히지 않았다). 대화의 AI 말풍선(첫 마디 포함)과 교정 카드의 고친 문장, 단어 카드(앞면 단어·뒷면 예문, 오답 복습 카드 포함), 빈칸 채점 뒤 정답을 채운 예문(`words.md`)에 둔다. 레벨업 테스트·종료 피드백·AI 해설·빈칸 보기에는 두지 않는다. 배치는 `ui.md`를 따른다.
- **만드는 곳**: 글자만 보고 규칙으로 바꾸면 조사 は·へ와 장음을 틀리므로 AI가 만든다(ADR-015).
  - 대화: 턴마다 Claude가 `reply_pron_ko`·`corrected_pron_ko`를 함께 만든다. 첫 마디는 `scenarios.ts`의 `pronKo`(레벨 1~3 상황)이며 첫 마디처럼 사람이 검수한다.
  - 단어: 미리 만들어 데이터에 저장한다(`words.md` "단어 데이터").
- **표기 규칙** (대화 프롬프트와 단어 생성 프롬프트가 같은 문구 `PRONUNCIATION_RULES`를 쓴다)
  - 소리 나는 대로 한글로만 쓴다. 가나·한자·로마자·숫자를 섞지 않는다. 한자는 `[漢字|かな]` 표기가 있으면 그 읽기대로 읽는다.
  - 가나 카드(`lib/kana`)와 같은 소리를 쓴다: か행 카·키·쿠·케·코, た행 타·치·츠·테·토, ず·づ 즈, じ·ぢ 지, ふ 후, を 오
  - 조사 は는 "와", 조사 へ는 "에"로 쓴다.
  - 장음은 `-`로 쓴다: 今日は → 쿄-와, 先生 → 센세-, ありがとう → 아리가토-, コーヒー → 코-히-, 難しい → 무즈카시-, いい → 이-. 동사 끝의 う는 장음이 아니다: 言う → 이우, 思う → 오모우
  - っ는 앞 글자의 ㅅ받침으로만 쓰고 따로 음절을 만들지 않는다: 学校 → 갓코-, 行って → 잇테, 間に合った → 마니앗타. 큰 つ는 받침으로 줄이지 않고 츠로 쓴다: 発言 → 하츠겐
  - ん은 ㄴ받침으로만 쓰고 따로 음절을 만들지 않는다: こんにちは → 콘니치와, 日本語 → 니혼고, 進んで → 스슨데
  - 요음: きゃ 캬, しゃ 샤, ちゃ 챠, じゃ 쟈, しょ 쇼, ちょ 쵸, にゅ 뉴 (나머지도 같은 방식). 조·초·추·주로 줄이지 않는다: 大丈夫 → 다이죠-부, お茶 → 오챠, 注意 → 츄-이
  - 문절마다 띄어 쓴다. 구두점은 。→ `.`, 、→ `,`, ？→ `?`, ！→ `!`로 바꾸고, 「」 같은 그 밖의 기호는 뺀다. 가타카나 이름의 ・는 띄어쓰기로 바꾼다.
  - 숫자는 읽는 대로 한글로 쓴다(3時 → 산지).
  - 예: `[今日|きょう]は[何|なに]をしますか。` → `쿄-와 나니오 시마스카.`
  - 위의 "따로 음절을 만들지 않는다"·"줄이지 않는다"·동사 う·しい·いい 예는 2026-10-14 단어 1,000개 검수에서 반복된 오류(오류 63건, 표기 통일 17건)로 더했다. 검수에서 틀렸던 62개 단어 중 위 예와 같은 단어가 나오는 것을 뺀 45개(필드 90개)를 다시 만들면 고친 값과 다른 필드가 25개에서 13개로 줄었다. おお 장음(이키도오루), 활용형의 っ(이타옷타), 큰 つ(싯몬)와 한자 오독은 남는다. 이 셋에 예(大きい·通る·知り合って·活動)를 더 넣어 봤지만 줄지 않아서(13 → 14) 넣지 않았다. 남는 오류는 대부분 상급·고수 어휘라 대화에서는 발음을 보여 주지 않는다.
- **검사**(`lib/pronunciation`): 앞뒤 공백을 지운 뒤 한글 음절·공백과 `-.,?!~…`만 있고 한글 음절이 하나 이상이면 쓴다. 쓸 때 받침을 규칙대로 맞춘다. 일본어 발음의 받침은 ん(ㄴ)과 っ(ㅅ)뿐이므로 ㅇ·ㅁ받침은 ㄴ으로(타쿠상 → 타쿠산, 옹가쿠 → 온가쿠), ㄱ·ㄷ·ㅂ받침은 ㅅ으로(각코- → 갓코-) 바꾼다. 2026-10-14 레벨 1 단어 생성에서 모델이 ん을 한국어 습관대로 ㅇ받침으로 쓴 값이 200개 중 9개 나왔다. 비었거나 그 밖의 글자(가나·한자·영문·숫자 등)가 있으면, 대화에서는 그 발음을 `null`로 저장해 숨기고 턴은 성공으로 처리한다. 단어 데이터에서는 검증 오류다.
- **화면 낭독기**: 발음 줄은 `aria-hidden`이다. 일본어 문장에 `lang="ja"`가 있어 한글 발음까지 읽으면 같은 내용을 두 번 듣게 된다. 새 턴 알림 영역에도 넣지 않는다.
- 발음은 대화 기록으로 Claude에 다시 보내지 않는다(기록에는 reply만 넣는다).

## 문장 뜯어보기 (2026-10-17 추가)
- **목적**: 번역과 교정 설명은 문장 전체를 한 번에 옮겨서, 문장의 어느 부분이 어떤 뜻인지 알 수 없다(2026-10-17 운영 확인에서 사용자가 지적). 문장을 의미 조각(단어·조사 묶음·서술어)으로 나눠 조각마다 한국어 뜻을 보여 준다.
- **대상과 위치**: 모든 언어·레벨. 대화의 AI 말풍선(첫 마디 포함)과 교정 카드의 고친 문장에 둔다. 종료 피드백, 단어, 레벨업 테스트에는 두지 않는다. 처음에는 닫혀 있고 [문장 뜯어보기]를 눌러 열고 닫는다. 배치는 `ui.md`를 따른다.
- **형식**: `[{ text, meaning_ko }]`. `text`는 문장에 나온 그대로의 조각이고, `meaning_ko`는 그 조각의 문장 속 뜻을 짧게 쓴 한국어다. 일본어 조각의 읽기 표기는 AI에게 요청하지 않는다. 검사를 통과하면 코드가 AI가 준 글자 대신 원래 문장(표기 포함)을 조각 경계에서 잘라 `text`로 저장한다. 그래서 타일의 읽기·대소문자·문장부호는 늘 말풍선·교정 문장과 같고 출력 토큰도 줄어든다. 조각 사이의 공백·문장부호는 앞 조각에 붙이고, 여는 괄호·따옴표(`「`, `(`, `“`)와 통화 기호(`$`)는 뒤 조각에 붙인다(`[彼|かれ]は` / `「[行|い]く」と`). 문장 맨 앞의 것은 첫 조각에 붙는다. 문장에 깨진 표기가 있으면 `parseFurigana`가 읽은 모양(화면에 보이는 모양)으로 다시 써서 자른다. 표기 하나가 두 조각에 걸치면 검사 실패로 본다. 조각은 문장 순서대로다. 조사·어미는 앞말과 묶는다(`[家|いえ]で` 집에서, `[休|やす]んでいました` 쉬고 있었어요. 영어는 `at home` 집에서).
- **만드는 곳**: 대화는 턴마다 Claude가 `reply_breakdown`·`correction.breakdown`을 함께 만든다(ADR-018). 첫 마디는 `scenarios.ts`의 `breakdown`이며 첫 마디·한글 발음처럼 AI로 초안을 만들고 사람이 검수한다.
- **검사**(`lib/breakdown`): 조각의 `text`를 순서대로 이어 붙인 것과 원래 문장을 비교한다. 둘 다 후리가나 표기를 지우고(`stripFurigana`), 공백·문장부호·기호(`\p{S}`)를 빼고, 영어는 대소문자를 무시한다. 공백·문장부호만 있는 조각(`?`)은 문장에서 자를 자리가 없으므로 빼고 검사한다. 그 글자는 위 규칙대로 이웃 조각에 붙는다. 모델이 끝 문장부호를 따로 조각으로 만들어도 뜯어보기 전체가 사라지지 않게 하려는 것이다(프롬프트에도 그런 조각을 만들지 말라고 쓴다). 같지 않거나, 남은 조각이 없거나, 남은 조각에 `meaning_ko`가 빈 것이 있으면 그 문장의 뜯어보기를 `null`로 저장해 버튼을 숨긴다. 턴은 성공으로 처리한다. 모델이 조각을 빼먹거나, 사전형으로 바꾸거나(`食べたり` → `食べる`), 한자를 가나로 바꾸면 대응이 틀려지기 때문이다. 첫 마디의 `breakdown`은 단위 테스트가 같은 검사로 확인한다.
  - 검사에 맞지 않으면 `console.warn`으로 `{ ai: "breakdown_invalid", target: "reply" | "corrected", language, level }` 한 줄을 남긴다(문장·조각 내용은 남기지 않는다). 통과율이 낮아 기능이 조용히 사라지는 것을 운영 로그로 알기 위해서다.
  - 구현 뒤 실제 턴 약 30개(언어·레벨 섞어서)로 검사 통과율, 응답 시간, 입출력 토큰을 재서 `usage.md`의 추정을 고친다. 통과율이 낮으면 프롬프트를 고친다. 유료 API 호출이므로 하네스 step 안에서 하지 않고 phase가 끝난 뒤 메인 세션에서 한다.
- **저장**: `chat_turns.reply_breakdown`(jsonb)과 `correction` jsonb 안의 `breakdown`. 기능을 넣기 전의 턴과 검사에 맞지 않은 문장은 없다(`null`·키 없음).
- 뜯어보기는 대화 기록으로 Claude에 다시 보내지 않는다(기록에는 reply만 넣는다). 새 턴 알림 영역(`aria-live`)에도 넣지 않는다.

## 세션 종료 피드백
- **시작 RPC**: `profiles → chat_sessions` 순서로 잠그고 만료 작업을 복구한다. 살아 있는 메시지 작업이 있으면 409, 이미 `ending`이면 202, `ended`이면 저장된 결과를 반환한다.
- `active`이고 성공한 턴이 있으면 `ending`, `feedback_status = pending`으로 전환하고 새 UUID 토큰과 90초 기한을 예약한다. 잠금을 해제한 뒤 예약을 얻은 요청만 Claude로 `{ good, improve[] }`를 생성한다. `improve`는 최대 3개로 저장한다.
- **완료 RPC**: 자신의 토큰·기한을 확인한 뒤 피드백 저장, `feedback_status = ready`, `status = ended`, `ended_at` 기록, 토큰 해제를 한 트랜잭션으로 처리한다.
- **생성 실패 또는 처리 기한 만료**: `feedback_status = fallback`, `status = ended`, `ended_at`과 고정 대체 결과를 함께 저장하고 토큰을 해제한다. 대체 결과는 `feedback = { message: "대화 기록은 저장됐어요. 종합 피드백을 만들지 못했으니 대화 아래의 교정을 확인해 주세요." }`이며, 실제 학습 평가처럼 꾸미지 않는다. 실패 확정과 `chat_failed` 기록은 한 번만 일어난다.
- 오늘 실패가 10회 이상이어도 종료는 가능하다. 이때는 Claude 호출 없이 같은 대체 결과로 끝내며 새 AI 실패로 세지 않는다. 이 기준은 새 AI 호출의 차단 기준이다. 다른 세션에서 이미 시작한 작업이 실패하면 당일 실패 기록은 10회를 넘을 수 있다.
- 종료 응답이 유실되거나 DB 저장 전에 서버가 중단돼도 다음 `/end`가 저장 결과 또는 기한 만료 복구 결과를 반환한다. 기한 내 DB 저장을 재시도할 때에도 AI 호출부터 반복하지 않는다. 대체 결과가 확정된 세션의 종합 피드백을 다시 생성하는 기능은 MVP에서 제외한다.
- AI가 레벨 조정을 제안하지는 않는다. 피드백은 잘한 점과 고칠 점만 준다. 레벨을 올리려면 홈의 레벨업 테스트로, 내리려면 홈에서 직접 바꾼다.

## 모델
환경변수 `CLAUDE_MODEL`로 바꿀 수 있고, 기본값은 `claude-sonnet-5-5`다. 2026-10-08 일본어 샘플 비교에서 Haiku 4.5는 후리가나 누락과 교정 누락이 잦아 바꿨다(ADR-012). `output_config.effort`를 받지 않는 모델(Haiku 4.5 등)로 바꾸면 모든 호출이 API 오류가 된다.
