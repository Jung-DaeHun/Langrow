# Langrow MVP 상세 설계 (spec)

> 상태: 구현 기준 (8장 "제품"의 미정 항목: 서비스 이름) · 작성일 2026-10-04 · 리뷰 반영: 동시성·종료 복구·지표·학습 완료 흐름 보완 · 2차: 지표 정의(유효한 세션·목표 완료·Pro 관심), 방문 기록 제거, 경로·레이어·TDD 규칙 정리
> 요약 규칙은 `CLAUDE.md`와 `docs/PRD.md`, `ARCHITECTURE.md`, `ADR.md`, `UI_GUIDE.md`에 있다. 이 문서는 상세 동작의 기준이다. 요약 문서와 다르면 이 문서를 따르고 요약 문서를 고친다.
> `docs/spec/`에 두는 이유: `scripts/execute.py`는 `docs/*.md`(하위 폴더 제외)만 매 step 프롬프트에 넣는다. 이 문서는 길어서 자동으로 넣지 않고, step 파일의 "읽어야 할 파일"로 지정한다.
>
> **원칙: 수요 검증에 필요 없는 것, 또는 없어도 사용자가 불편하지 않은 것은 만들지 않는다.**

## 1. 유저 저니

**대표 사용자 2명** (흐름을 검증하는 기준)
- **민지 (28, 직장인)**: 영어 회화를 다시 시작하려는 중급 학습자. 출퇴근 15분 동안 모바일로 학습한다.
- **준호 (21, 대학생)**: 일본 여행을 앞두고 일본어를 처음 배우는 입문자. 히라가나는 일부만 읽는다.

**단계별 저니**

| 단계 | 사용자 마음 | 화면과 행동 | 확인할 지표 |
|---|---|---|---|
| ① 발견 | "나한테 맞나?" | 랜딩: 가치 제안 한 줄, 교정 예시가 담긴 샘플 대화(정적 이미지), 기능 소개(레벨업 카드에 5단계 안내), Free/Pro 비교 | 신규 가입 수 (로그인 전 클릭 추적은 MVP 제외) |
| ② 가입 | "빨리 해 보자" | 구글 로그인 1클릭 | 가입 수 |
| ③ 온보딩 | "내 수준에 맞게" | 약관 동의(체크 1개) → 언어 → 레벨 | 온보딩 완료율 |
| ④ 첫 경험 | "진짜 고쳐 주네" | 홈의 "오늘 할 일"이 안내 → 첫 롤플레이 → 교정 → 종료 피드백 | 첫 세션 완료율 |
| ⑤ 매일 학습 | "오늘 할 것만" | 오늘 할 일 2개(단어 10개, 대화 1세션) + 연속 학습일 | D1·D7 학습 재참여율 |
| ⑥ 한도 도달 | "오늘 할 일 끝, 더 할까?" | 한도 안내 → [7일 무료 체험 시작]. Free 단어 한도는 오늘 목표와 같아서 목표를 마치면 도달한다 | 목표 완료·한도 도달 → 체험 전환율 |
| ⑦ 체험 중 | "Pro는 이렇구나" | 늘어난 한도, 상단에 "체험 n일 남음" | 체험 중 사용량이 Free 한도를 넘는지 |
| ⑧ 체험 종료 | "계속 쓸까?" | Free로 돌아감 → Pro 버튼을 누르면 "정식 출시 준비 중" | 체험 후 Pro 클릭 |
| ⑨ 성장 | "실력이 늘었다" | 레벨업 테스트 → 합격 축하 / 불합격 결과 | 응시율, 합격률 |

**화면 이동**
```
[랜딩] ─구글 로그인→ [온보딩: 동의 → 언어 → 레벨] ─→ [홈]

[홈] ├─ 오늘의 단어 → 플래시카드 → 빈칸 → 결과 ─→ [홈]
     ├─ AI 대화 → 상황 목록 → 대화 → 종료 피드백 ─→ [홈]
     ├─ 이어서 대화하기 (끝나지 않은 세션이 있을 때) → 대화
     ├─ 오답 복습 → 플래시카드 ─→ [홈]
     ├─ 레벨업 테스트 → 20문제 → 합격/불합격 ─→ [홈]
     ├─ 가나 익히기 (일본어 입문·초보) → 행 선택 → 플래시카드 ─→ [홈]
     └─ 계정 → 7일 체험 시작 / 로그아웃
```

**홈 구조** (위에서부터)
1. **상단**: 현재 언어·레벨, 🔥 연속 n일째. 체험 중이면 "체험 n일 남음", 체험이 끝났으면 "체험이 끝났어요"
   - 언어·레벨을 누르면 언어 전환과 레벨 내리기 메뉴가 열린다. 레벨이 있는 언어는 바로 전환하고, 처음 배우는 언어는 `/onboarding?language=ja`처럼 언어를 정한 채 레벨 단계로 보낸다.
2. **오늘 할 일** (진행률 포함. 학습 기록이 없는 사용자(`last_study_date` 없음)에게는 대화 카드를 "여기서 시작하세요"로 강조한다. 저니 ④와 첫 세션 완료율에 맞춘 것이며 카드 순서는 아래 그대로다)
   - ① 오늘의 단어 `min(x, 10)/10`. `x`는 오늘 처음 학습한 단어 수이며 언어를 합산한다.
   - 현재 레벨에 새 단어가 없으면 분모 10인 미완료 목표 대신 "이 레벨의 새 단어를 모두 학습했어요"를 보여 준다. 레벨 1~4는 테스트와 복습, 레벨 5는 복습과 대화로 안내한다. 그날 이미 10개를 채웠으면 오늘 목표 완료 표시도 유지한다.
   - ② 대화 1세션 (오늘 성공한 턴이 3개 이상인 세션이 있으면 완료). **유효한 대화 세션**은 성공한 턴이 3개 이상인 세션이며, [대화 끝내기]를 눌렀는지와 무관하다. 목표와 첫 세션 완료율 모두 이 기준을 쓴다.
   - 기본 목표는 플랜과 상관없이 같다. Pro는 목표를 넘어서 더 할 수 있다. 새 단어 소진으로 목표가 대체되어도 연속 학습일은 실제 학습 성공으로만 갱신한다.
3. **이어서 대화하기**: 현재 언어의 `active` 세션 중 가장 최근 것 1개를 보여 준다. `ending` 세션은 별도 "피드백 확인" 링크로 열어 종료 처리를 다시 확인한다.
4. **오답 복습 n개**, **레벨업 테스트**(레벨 1~4일 때 항상 보임), (일본어 입문·초보이면) **가나 익히기**

**연속 학습일** (`profiles.last_study_date`, `profiles.streak` 컬럼 2개)
- **갱신 시점**: 대화 턴 성공, 신규 단어가 있는 회차 저장, 유효한 복습 회차 저장, 가나 회차 완료, 유효한 레벨업 테스트 제출. 중복 단어 저장, 빈 회차, 단순 방문, 0턴 종료는 제외한다.
- 학습 결과와 같은 DB 트랜잭션에서 당일 `user_activity_days` 행과 연속 학습일을 기록한다. `profiles` 행을 잠그고 DB 시각으로 계산해 동시 요청이 연속일을 덮어쓰지 않게 한다.
- **갱신 규칙**
  - `last_study_date`가 오늘(한국 시간)이면 그대로 둔다.
  - 어제이면 `streak + 1`로 올린다.
  - 그 밖에는 1로 시작한다.
- **표시**: `last_study_date`가 오늘이나 어제면 `streak`를 보여 주고, 아니면 0을 보여 준다.
- 언어와 상관없이 하나의 연속일로 센다. 오늘 할 일을 다 마치지 않아도 인정된다.

**예외 흐름**

| 상황 | 흐름 |
|---|---|
| 대화 도중 이탈했다가 돌아옴 | 홈의 "이어서 대화하기"로 이어서 한다. 전송 중이면 완료를 기다리고, 처리 기한이 지났으면 다음 대화 API 요청에서 복구한다 |
| 대화 도중 한도에 도달 | 서버가 `429 LIMIT_REACHED`를 반환하면 입력이 막힌다. 표시된 남은 횟수만으로는 막지 않는다. [대화 끝내기]로 피드백은 받을 수 있고, 체험 안내를 보여 준다 |
| 대화 도중 체험이 끝남 | 다음 메시지부터 Free 한도가 적용된다 |
| 단어 회차 도중 이탈 | 저장되지 않는다. 다음에 같은 단어부터 다시 시작한다 |
| 오늘 단어 한도를 채움 | "오늘 단어 완료!"를 보여 주고 대화를 안내한다. 새 단어가 더 남은 Free 사용자에게는 체험 안내도 보여 준다 |
| 언어를 바꿈 | 처음 배우는 언어면 레벨 선택부터 한다 |
| 레벨을 내림 | 확인 대화상자를 거쳐 바로 바뀐다 |
| 레벨 1~4의 단어를 모두 학습함 | 새 단어 완료 화면에서 레벨업 테스트와 오답 복습으로 안내한다 |
| 레벨 5의 단어를 모두 학습함 | "고수 단계의 새 단어를 모두 학습했어요"와 오답 복습·AI 대화 버튼을 보여 준다. 오답이 없으면 대화만 안내한다 |
| 일본어 입문자가 가나를 못 읽음 | 온보딩의 일본어 입문 카드에서 가나 익히기를 안내하고, 홈의 가나 익히기 카드로 시작한다 |
| 구글 로그인 취소·실패 | `/?login=failed`로 돌아와 "로그인을 완료하지 못했어요"를 보여 준다 |
| 온보딩 도중 이탈 | 다음 방문 때 온보딩의 해당 단계부터 다시 시작한다 |
| 두 탭에서 같은 세션에 동시 전송 | 진행 중인 턴이 있으면 두 번째 요청은 409. 턴 처리 중 종료도 409이며 전송 완료 후 다시 종료할 수 있다 |
| 종료 요청 중 재요청·새로고침 | 처리 중이면 202와 재확인 간격, 완료됐으면 저장한 동일 결과를 반환한다 |
| 종료 피드백 생성 실패·처리 기한 초과 | 고정 안내와 이미 저장된 턴별 교정을 보여 주고 세션 종료를 완료한다 |
| 단어 저장 응답 유실·두 탭 재전송 | 이미 저장된 단어는 변경 없이 성공으로 응답한다. 신규 단어만 계정 공통 한도에 포함한다 |

### 화면 목록

| 경로 | 내용 |
|---|---|
| `/` | 서비스 소개, Free/Pro 비교, 구글 로그인 |
| `/auth/callback` | OAuth 콜백. `profiles`가 없으면 생성한다 |
| `/onboarding` | ① 약관 동의 (처음 한 번. "이용약관·개인정보처리방침(국외 이전 포함)에 동의하며 만 14세 이상입니다" 필수 체크) ② 언어 ③ 레벨 카드 5개 (일본어 입문 카드에는 가나 안내). 끝나면 `/home`으로 간다. 온보딩을 마친 사용자가 새 언어를 추가할 때는 `language` 파라미터로 ③만 쓴다 |
| `/home` | 위 "홈 구조" 참고. 오늘 남은 사용량도 보여 준다 |
| `/chat` → `/chat/[id]` | 현재 레벨의 상황 목록 → 대화 |
| `/words` | 오늘의 학습(플래시카드 → 빈칸) / 오답 복습 탭 |
| `/level-up` | 레벨업 테스트 20문제 → 결과 (경로에 `test`를 넣지 않는 이유는 6-9 참고) |
| `/kana` | 히라가나/가타카나 탭 → 행 선택 → 플래시카드 |
| `/account` | 플랜 비교, 7일 무료 체험 시작, 탈퇴 문의 안내, 로그아웃 |
| `/privacy`, `/terms` | 개인정보처리방침(국외 이전 포함), 이용약관. 로그인 없이 볼 수 있는 정적 페이지 |

- **레벨은 언어별로 저장한다.** 자유롭게 고를 수 있는 건 해당 언어를 처음 시작할 때뿐이다. 그 뒤에는 내리기만 직접 할 수 있고, 올리기는 레벨업 테스트로만 한다.
- 보호된 학습 페이지에서 동의(`agreed_at`)가 없거나 현재 언어의 레벨이 없으면 `/onboarding`으로 보낸다. `/onboarding` 자체와 공개 페이지에는 이 이동 규칙을 적용하지 않는다.
- API도 같은 준비 상태를 검증한다. 동의·첫 레벨 설정·언어 전환의 예외는 6-4에 명시하며, 페이지 이동만으로 API 사용을 제한하지 않는다.

**지표 수집**
- 이벤트(`events`)는 다른 테이블로 알 수 없는 것만 남긴다: `limit_reached`, `pro_clicked`, `kana_studied`, `level_test_submitted`, `chat_failed`(운영용).
- `limit_reached`는 서버가 성공한 학습으로 당일 한도를 채웠을 때, 또는 유효한 신규 학습 요청을 한도로 거부할 때 기록한다. UI가 추가 입력을 막아도 한도 도달을 놓치지 않게 한다. `props`에는 `feature(chat/words)`, `plan(free/pro)`, `trial_eligible`을 서버가 넣는다. 체험이 남은 Free 사용자의 첫 한도 도달만 체험 전환율의 출발점이 된다.
  - **해석**: Free 단어 한도(10개)는 오늘 목표와 같으므로 `feature = words`인 도달은 "추가 학습 의도"가 아니라 "오늘 목표 완료"를 뜻한다. 대화 한도(20턴)는 목표(유효한 세션 1개)보다 크므로 `feature = chat`인 도달은 목표 이상의 사용이다. 전환율은 `feature`별로 나눠 보고한다.
- 학습한 날은 `user_activity_days(user_id, activity_date)`에 한국 날짜별 한 행으로 보존한다. 학습 성공과 같은 트랜잭션에서 `insert … on conflict do nothing`으로 기록하며, 단순 방문은 기록하지 않는다.
  - 단어 복습·가나·레벨업 테스트만 한 날도 기록된다. `last_study_date`나 덮어쓰는 `updated_at`으로 과거 활동을 복원하지 않는다.
- 나머지는 원래 테이블에서 계산한다.
  - 가입: `profiles.created_at`
  - 온보딩 완료: 동의와 첫 언어·레벨 저장이 모두 끝난 시점의 `profiles.onboarded_at` (최초 한 번만 저장)
  - 첫 세션 완료: 첫 유효한 대화 세션(같은 세션의 성공한 `chat_turns` 3개 이상)의 3번째 성공 턴 `created_at`. 세션 종료 여부는 보지 않는다
  - 새 단어: `user_words.first_seen_at`
  - 체험: `profiles.trial_started_at`; 체험 중 초과 사용은 한국 날짜별 턴·새 단어 수
- 제품 전환율은 분모·분자 모두 distinct `user_id`로 계산한다. **사용량 한도와 하루 AI 실패 10회는 사용자 수가 아니라 각각 행 수·실패 횟수**로 센다.
- 방문 추적(비로그인 방문·로그인 버튼 클릭, 로그인 후 페이지 방문)은 MVP에서 제외한다. 가입 전 퍼널 전환율과 단순 재방문율은 보고하지 않는다.
- **계산 위치**: `scripts/metrics-report.ts`가 로컬에서 secret key로 원본 테이블을 읽고, `lib/metrics`의 순수 함수로 지표를 계산해 지표마다 분자/분모를 출력한다. 대시보드·관리자 화면은 만들지 않는다.

**수요 검증 기준 (첫 실험의 가설값)**
- 모집 기간은 출시일부터 28일, 목표는 온보딩 완료 사용자 50명이다. 각 사용자를 온보딩 완료 후 28일 관찰하고, 아래 지표마다 관찰 기간이 끝난 사용자만 분모에 넣는다. 운영자·테스트 계정은 로컬 환경변수 `METRICS_EXCLUDED_USER_IDS`(쉼표 구분)로 제외한다.
- 온보딩 완료일의 한국 날짜를 D0로 둔다. D1/D7은 각각 정확히 다음 날/7일 뒤에 `user_activity_days` 행이 있는지로 판단한다 (학습 재참여율).

| 지표 | 분모와 관찰 구간 | 첫 실험의 판단 기준 |
|---|---|---|
| 온보딩 완료율 | 가입 후 24시간이 지난 가입자 중 24시간 안에 온보딩 완료 | 60% 이상 |
| 첫 세션 완료율 | 온보딩 후 24시간이 지난 사용자 중 그 기간에 유효한 대화 세션(성공 턴 3개 이상)이 있음 | 50% 이상 |
| D1 / D7 학습 재참여율 | 각 관찰 날짜가 끝난 온보딩 완료 사용자 중 해당 날짜에 실제 학습 | 각각 30% / 15% 이상 |
| 목표 완료·한도 도달 → 체험 | 온보딩 후 첫 7일 안에 체험 가능한 Free 한도에 처음 도달한 사용자 중 도달 후 7일 안에 체험 시작. `feature`(단어=목표 완료, 대화=목표 이상 사용)별로도 나눠 보고 | 분모 20명 이상에서 20% 이상 |
| 체험 후 Pro 관심 (참고) | 경로와 무관하게 온보딩 후 14일 안에 체험을 시작했고, 체험 종료 후 7일이 지난 사용자 중 종료 후 7일 안에 Pro 클릭 | 기준 없음. 분자/분모만 보고 |

- 전체 온보딩 표본이 50명 미만이거나 개별 지표의 최소 표본이 부족하면 해당 판단은 보류한다. 비율에는 반드시 실제 분자/분모를 붙인다.
- 체험 후 Pro 관심은 50명 규모에서 표본이 수 명에 그치므로 판단 기준으로 쓰지 않고 참고만 한다 (예: 체험 전환 20%면 한도 도달 20명 중 체험 4명).
- 첫 세션 완료율과 D1/D7 기준을 만족하면 반복 학습 가치의 신호로 본다. 목표 완료·한도 도달 → 체험 기준까지 만족하면 결제 실험을 준비하며, 체험 후 Pro 관심의 분자/분모를 함께 참고한다. 부족하면 이탈 구간을 먼저 개선한 뒤 다시 측정한다.
- 무료 체험·Pro 클릭은 구매 의향의 간접 지표다. 실제 지불 의사는 결제 실험 전까지 검증됐다고 표현하지 않는다. 기준은 관찰 전에 고정하고 결과를 보고 소급 변경하지 않는다.

## 2. AI 대화

**상황 목록**
- 코드 상수(`src/lib/scenarios.ts`)로 둔다. 레벨당 4개, 총 20개이며 영어와 일본어가 같은 목록을 쓴다.
- 상황마다 `id / 제목 / 사용자 목표`는 공통으로, `AI 역할·배경 / 첫 마디`는 en과 ja 각각 정의한다.
  - 첫 마디에는 한국어 번역을 붙이고, 일본어는 후리가나 표기를 포함한다.
  - 초안은 AI로 만들어도 되지만, 사람이 검수한 뒤 코드에 넣는다.
- 문화적 배경은 언어별 데이터에서 사람이 정한다 (예: 영어는 미국 카페, 일본어는 편의점). 첫 마디가 이미 배경을 정하므로 AI가 바꾸지 않는다.

**대화 진행**
1. 현재 레벨의 상황을 고르면 세션을 만들고 **고정된 첫 마디**를 보여 준다.
   - 이때 Claude를 부르지 않는다. 다른 레벨의 상황이면 400을 돌려준다.
2. 사용자 발화마다 Claude로 응답 하나를 생성하고 아래 구조로 받는다 (zod로 검증). 실패 시 재시도는 6-6의 최대 1번 규칙을 따른다.
   ```
   { reply: string,                 // AI의 다음 대사
     reply_ko: string,              // reply의 한국어 번역
     correction: { corrected: string, explanation_ko: string } | null }
   ```
3. 교정은 사용자 메시지 바로 아래에 보여 준다. 틀린 게 없으면(`null`) 보여 주지 않는다.
4. 입문·초보는 한국어로 입력해도 된다. 그러면 교정란에 "이렇게 말하면 돼요"가 나온다.
   - 입력에 한국어가 들어 있으면 `correction`은 `null`이 아니다. 한국어 문장이 자연스러워도 마찬가지다. `corrected`는 사용자의 말을 학습 언어로 옮긴 문장이고, `explanation_ko`는 핵심 표현을 짧게 설명한다.
   - 한국어 문장 자체의 맞춤법·표현은 고치거나 평가하지 않는다.
   - 한국 사람 이름·지명은 일본어에서는 가타카나(정대훈 → チョン・デフン), 영어에서는 로마자로 쓴다. 한글을 학습 언어 문장에 섞지 않는다.
5. **한 세션은 최대 20턴이다.** 20번째 응답에 `turnsLeft: 0`이 담겨 오면, 클라이언트가 이어서 `/end`를 호출한다. 대화 응답과 피드백을 한 요청에서 처리하지 않는다.
6. **`/end`는 멱등이다.** 세션 상태는 `active → ending → ended`로 이동한다.
   - 종료 처리 중에는 새 메시지를 받지 않는다. 유효한 턴이 처리 중이면 종료 요청을 409로 거부한다.
   - 이미 `ending`이면 Claude를 다시 부르지 않고 `202 { status: 'ending', retryAfterSeconds: 2 }`를 반환한다. 클라이언트는 화면이 보이는 동안 간격을 두고 `/end`를 재호출하고, 화면에 돌아오면 재개한다.
   - `ended`이면 저장된 피드백과 `feedback_status`를 그대로 반환한다. 처리 실패도 고정 대체 결과로 종료하므로 다음 요청에서 복구할 수 있다.
   - 성공한 턴이 0개인 세션은 Claude를 부르지 않고 `ended`, `feedback_status = skipped`로 끝낸다.
7. **입력은 1~300자다.** 앞뒤 공백을 제거한 뒤 센다. 클라이언트와 서버가 같은 함수(`lib/text`)로 센다.
8. 스트리밍 없이 응답을 한 번에 받는다.
9. **IME 처리**: 조합 중(`isComposing`)일 때 누른 Enter로는 전송하지 않는다. 한글·일본어 입력이 반쯤 전송되는 버그를 막기 위해서다.

**대화 1턴 처리 (트랜잭션으로 예약 → AI 호출 → 결과 확정)**

한 턴은 `chat_turns`의 한 행이다. 동일 세션의 진행 중인 작업은 하나만 허용한다.

1. 로그인·동의·온보딩 상태와 입력을 확인한다. 세션을 `id + user_id`로 조회하며 없거나 남의 세션이면 404다. 세션에 저장된 언어·레벨로 이어서 대화한다.
2. **예약 RPC**: `profiles` 행을 잠근 뒤 해당 사용자의 만료된 작업을 복구하고 대상 세션을 잠근다. 아래 검사와 예약을 하나의 짧은 트랜잭션에서 처리한다.
   - `status != active`이거나 유효한 `operation_token`이 있으면 409다. `unique(session_id, turn_no)`만으로 실행을 잠그지 않는다.
   - 오늘 `chat_failed`가 10개 이상이면 `429 AI_FAILURE_LIMIT`다.
   - 성공한 세션 턴이 이미 20개면 `409 SESSION_FULL`이다.
   - 오늘 계정의 `pending + done` 턴이 플랜 한도에 도달했으면 예약 없이 `limit_reached`를 기록하고 `429 LIMIT_REACHED`를 반환한다.
   - `turn_no = 마지막 done 턴 + 1`로 `pending`을 생성한다. 그 행의 UUID를 세션 `operation_token`으로 저장하고 `operation_expires_at = DB 현재 시각 + 90초`로 둔다. 커밋 후에도 pending 예약은 한도에 포함된다.
3. **Claude 호출**: DB 잠금을 해제한 뒤 시스템 프롬프트 + 첫 마디 + 순서대로 정렬한 `done` 턴들 + 이번 입력을 보낸다.
4. **성공 확정 RPC**: 같은 잠금 순서로 `active` 상태, 요청의 토큰 일치, 기한 내 처리, 해당 pending 행을 확인한다. 응답 저장·`done` 전환·토큰 해제·활동일/연속일 갱신을 함께 커밋하고 `turnsLeft`를 반환한다. 오늘 예약된 done 턴 수가 한도에 도달하면 같은 트랜잭션에서 `limit_reached`도 기록한다.
5. **실패 확정 RPC**: 해당 작업을 아직 소유한 경우에만 pending 삭제·예약 반환·토큰 해제·`chat_failed` 기록을 함께 커밋한 뒤 `503 AI_UNAVAILABLE`을 반환한다. 재시도까지 실패한 작업당 한 번만 기록하며, `props`에 `operation_token`, `kind(turn/feedback)`, 실패 사유를 넣는다.
6. 이미 복구됐거나 기한이 지난 토큰으로 온 결과는 저장하지 않고 409로 처리한다. 늦은 성공/실패 응답이 새 작업을 변경하거나 같은 실패를 다시 기록해서는 안 된다.

**처리 중단 복구**
- 대화 세션 생성·메시지·종료 API의 쓰기 RPC는 `profiles` 잠금을 잡은 뒤 해당 계정의 만료된 작업을 복구한다. 성공/실패 확정 RPC도 자신의 작업이 만료됐으면 같은 복구 규칙을 적용한다.
- `active`의 만료된 작업: 해당 토큰의 pending 행만 삭제하고 토큰을 해제한다. 실패 이벤트는 한 번 기록하며 사용자는 다시 전송할 수 있다.
- `ending`의 만료된 작업: 아래 고정 대체 피드백으로 `ended`를 확정한다. AI를 다시 호출하지 않는다.
- 기한은 AI 요청 전체 예산(최대 약 40초)과 라우트 실행 상한(60초)보다 긴 90초다. 예약·판정 시각은 DB 기준이며, 복구 뒤 도착한 결과는 토큰으로 차단한다.
- 정리용 cron은 두지 않는다. 아직 처리 기한이 남은 작업은 409/202로 안내하고 만료 뒤 다음 API 요청에서 복구한다. 클라이언트는 표시된 남은 사용량으로 입력을 막지 않고, 서버의 `429` 응답 뒤에만 막는다. 만료된 pending이 표시 사용량에 포함돼 있어도 실제 한도는 서버의 복구 후 판정에 따른다.
- 네트워크가 끊긴 뒤 이미 성공한 메시지를 사용자가 다시 전송하는 중복은 MVP에서 감수한다. 메시지 멱등 키는 도입하지 않는다.

**레벨별 조절** (시스템 프롬프트에 레벨 지침을 넣는다)

| 레벨 | AI 문장 | 교정 강도 | 번역 | 일본어 후리가나 |
|---|---|---|---|---|
| 입문 | 아주 짧고 쉬운 표현 | 의미가 안 통하는 오류만 | 기본 표시 | 모든 한자 |
| 초보 | 짧은 문장 | 주요 문법 | 기본 표시 | 모든 한자 |
| 중급 | 일상 수준 | 문법 + 어색한 표현 | 눌러서 보기 | 모든 한자 |
| 상급 | 자연스러운 속도 | 뉘앙스까지 | 눌러서 보기 | 없음 |
| 고수 | 원어민 수준, 관용구 | 뉘앙스·격식까지 | 눌러서 보기 | 없음 |

- **후리가나**: AI가 `[漢字|かんじ]` 형식으로 출력하면, 프론트에서 `<ruby>` React 요소로 그린다. 표기는 한자에만 단다(가나·한글에는 달지 않는다).
  - AI 출력을 HTML로 넣지 않는다.
  - 표기가 깨져 있으면 괄호 기호를 지우고 일반 텍스트로 보여 준다.
  - 본문에 한자가 없는 표기(`[コーヒー|こーひー]`, 한글 이름 등)는 읽기를 버리고 본문만 보여 준다.
  - 종료 피드백(잘한 점·고칠 점)과 턴 교정의 설명(`explanation_ko`)은 표기를 요청하지 않지만 모델이 교정 문장이나 대화 기록의 표기를 따라 쓸 수 있으므로 같은 규칙으로 그린다.
- **프롬프트 인젝션**: 시스템 프롬프트로 역할을 유지하게 하고, 출력은 스키마로 강제한다. 남용 비용의 상한은 300자, 20턴, 일일 한도가 정한다.

**세션 종료 피드백**
- **시작 RPC**: `profiles → chat_sessions` 순서로 잠그고 만료 작업을 복구한다. 살아 있는 메시지 작업이 있으면 409, 이미 `ending`이면 202, `ended`이면 저장된 결과를 반환한다.
- `active`이고 성공한 턴이 있으면 `ending`, `feedback_status = pending`으로 전환하고 새 UUID 토큰과 90초 기한을 예약한다. 잠금을 해제한 뒤 예약을 얻은 요청만 Claude로 `{ good, improve[] }`를 생성한다. `improve`는 최대 3개로 저장한다.
- **완료 RPC**: 자신의 토큰·기한을 확인한 뒤 피드백 저장, `feedback_status = ready`, `status = ended`, `ended_at` 기록, 토큰 해제를 한 트랜잭션으로 처리한다.
- **생성 실패 또는 처리 기한 만료**: `feedback_status = fallback`, `status = ended`, `ended_at`과 고정 대체 결과를 함께 저장하고 토큰을 해제한다. 대체 결과는 `feedback = { message: "대화 기록은 저장됐어요. 종합 피드백을 만들지 못했으니 대화 아래의 교정을 확인해 주세요." }`이며, 실제 학습 평가처럼 꾸미지 않는다. 실패 확정과 `chat_failed` 기록은 한 번만 일어난다.
- 오늘 실패가 10회 이상이어도 종료는 가능하다. 이때는 Claude 호출 없이 같은 대체 결과로 끝내며 새 AI 실패로 세지 않는다. 이 기준은 새 AI 호출의 차단 기준이다. 다른 세션에서 이미 시작한 작업이 실패하면 당일 실패 기록은 10회를 넘을 수 있다.
- 종료 응답이 유실되거나 DB 저장 전에 서버가 중단돼도 다음 `/end`가 저장 결과 또는 기한 만료 복구 결과를 반환한다. 기한 내 DB 저장을 재시도할 때에도 AI 호출부터 반복하지 않는다. 대체 결과가 확정된 세션의 종합 피드백을 다시 생성하는 기능은 MVP에서 제외한다.
- AI가 레벨 조정을 제안하지는 않는다 (S1). 레벨을 올리려면 홈의 레벨업 테스트로, 내리려면 홈에서 직접 바꾼다.

**모델**: 환경변수 `CLAUDE_MODEL`로 바꿀 수 있고, 기본값은 `claude-haiku-4-5-20251001`이다. 출시 전에 일본어 교정 품질을 샘플로 확인한다.

## 3. 단어 학습

**단어 데이터: 미리 생성**
- `scripts/generate-words.ts`로 **언어 × 레벨마다 200개**를 만든다.
- `data/words/{en,ja}-{1..5}.json`에 커밋해서 검수하고, seed로 DB에 넣는다. 레벨 안의 순서는 빈도 순위(`rank`)를 따르며, 품사(명사·동사·형용사·부사 등)를 가리지 않고 섞는다.
- 같은 언어의 낮은 레벨에 있는 단어는 다시 넣지 않는다. 그래서 레벨 1부터 순서대로 만든다.

| 필드 | 영어 예 | 일본어 예 |
|---|---|---|
| id | `en-1-001` | `ja-1-001` |
| word / reading | go / – | 行く / いく |
| meaning_ko | 가다 | 가다 |
| example (정답 위치 `{{ }}`) | `I {{went}} to school.` | `[学校\|がっこう]に{{[行\|い]った}}。` |
| example_ko | 나는 학교에 갔다. | 학교에 갔다. |
| distractors (모든 레벨, 3개) | goes, gone, going | `[行\|い]く`, `[行\|い]って`, `[行\|い]かない` |

- distractors는 그 문장에 넣으면 틀리는 보기다. 정답과 다른 형태를 3개 만들 수 있는 단어(동사 등)는 같은 단어의 다른 형태를 쓴다. 만들 수 없는 단어(명사·부사 등)는 `example_ko`의 뜻과 맞지 않는 같은 품사의 다른 단어를 쓴다(예: `{{[水\|みず]}}を[飲\|の]みたいです。` / 물을 마시고 싶어요 → `[本\|ほん]`, `[駅\|えき]`, `[先生\|せんせい]`). 빈칸 화면이 한국어 문장을 함께 보여 주므로 정답이 하나로 정해진다.
- 보기는 활용 어미를 자르지 않은 완전한 형태로 쓴다(`[違\|ちが]わ`, `[重\|おも]けれ`가 아니라 `[違\|ちが]わない`, `[重\|おも]ければ`).
- 일본어는 정답과 오답 보기에도 후리가나 표기를 쓰고, 레벨 규칙(입문~중급만 후리가나 표시)에 따라 그린다.

**오늘의 학습 (회차 최대 10개)**
1. **회차 크기**는 `min(10, 오늘 남은 한도, 선택한 언어·레벨의 미학습 단어 수)`다. Free는 하루 총 10개, Pro는 총 30개까지다. 레벨 끝에서는 10개 미만의 회차도 허용한다.
2. **플래시카드**: 아직 안 본 단어를 `rank` 순서로 보여 준다. [알아요]/[모르겠어요]는 클라이언트에만 기록해 둔다.
3. **빈칸 채우기**: 같은 단어들로 한국어 문장과, 빈칸이 뚫린 외국어 문장을 보여 준다.
   - **모든 레벨이 4지선다다** (S2). 보기는 정답과 `distractors`를 섞어서 만든다.
   - 고른 보기가 `{{ }}` 안의 표기와 같으면 정답이다 (`lib/blank`). 문자열을 그대로 비교하므로 정규화가 필요 없다.
4. **회차가 끝나면 한 번만 저장한다** (`POST /api/words/batch`)
   - body: `{ language, items: [{ word_id, knew, correct }] }`. language는 회차 시작 때 고정한다.
   - [알아요]를 누르고 빈칸도 맞혔으면 `known`, 그 밖에는 `review`가 된다. 신규 단어에만 `first_seen_at`을 기록한다.
5. **중간에 나가면 저장하지 않는다.** 다음에 같은 단어부터 다시 나온다. AI 비용이 없으니 문제없다.
6. **저장 RPC: 중복 제거·한도 확인·신규 저장을 같은 트랜잭션에서 처리한다.**
   - 로그인·동의·온보딩을 확인하고 `profiles` 행을 잠근다. 명시한 언어의 레벨이 있어야 하며, items는 서로 다른 word_id 1~10개여야 한다. 모든 단어가 존재하고 명시한 언어에 속하는지 검사한다.
   - 이미 이 사용자의 `user_words`에 있는 단어는 제외한다. 전부 기존 단어면 **한도가 0이어도 200, insertedCount = 0**이다. 기존 상태·날짜·연속일·학습 활동을 변경하지 않는다.
   - 남은 신규 단어는 DB 현재 시각의 플랜과 계정 전체 오늘 사용량으로 한도를 확인한다. 단어의 레벨은 검사하지 않는다 (다른 레벨 단어를 저장해도 본인 손해일 뿐이다). 다른 탭의 언어 전환·레벨 변경은 영향을 주지 않는다.
   - 신규 개수가 남은 한도를 넘으면 신규 단어는 하나도 저장하지 않고 `limit_reached`와 `429 LIMIT_REACHED`를 반환한다. 기존 단어와 신규 단어가 섞여도 신규분만 판정한다.
   - 허용되면 신규 행 삽입과 활동일·연속일 갱신을 함께 커밋하고 실제 `insertedCount`를 돌려준다. 저장 후 오늘 한도를 채웠으면 `limit_reached`도 같은 트랜잭션에 기록한다. 같은 계정의 모든 회차가 이 잠금을 사용하므로 두 탭·두 언어의 동시 저장도 계정 한도를 넘지 않는다.
   - `on conflict do nothing`은 PK 중복의 보조 방어이며 한도 판정이나 성공 응답을 대신하지 않는다.
7. 홈의 진행률과 새 단어 소진 표시는 1장의 홈 규칙을 따른다. 한도 도달과 학습할 단어가 없는 상태를 구분한다.

**새 단어 소진**
- 레벨 1~4: 완료 화면에서 레벨업 테스트와 현재 언어의 오답 복습으로 안내한다. 테스트에 합격하면 새 레벨의 미학습 단어를 제공하며 당일 계정 한도는 유지한다.
- 레벨 5: "고수 단계의 새 단어를 모두 학습했어요"를 보여 주고 오답 복습과 AI 대화로 안내한다. 레벨업 버튼·불가능한 단어 10개 목표·새 단어 추가를 약속하는 체험 안내는 표시하지 않는다.
- 오답이 0개면 복습 버튼 대신 "복습할 오답이 없어요"와 대화 버튼을 보여 준다. 레벨이나 언어를 바꿔 새 단어가 생기면 일반 학습 화면으로 돌아간다.

**오답 복습**
- 현재 언어의 `review` 단어를 최대 10개씩 플래시카드로 다시 본다. 끝나면 `POST /api/words/review`로 `{ language, items: [{ word_id, knew }] }`를 저장한다.
- 사용자 소유의 해당 언어 학습 기록만 허용한다. `profiles`를 잠근 트랜잭션에서 여전히 `review`인 제출 단어를 확인하고 [알아요]는 `known`, 나머지는 `review`로 둔다. 유효한 review 단어가 하나 이상인 회차만 활동일·연속일을 갱신한다. 전부 이미 known이면 변경 없이 성공한다.
- 사용량에 포함하지 않는다. 레벨을 바꿔도 이전 레벨의 오답은 남아 있다.

## 3-1. 가나 익히기 (일본어 전용)

- **대상**: 가나를 다 읽지 못하는 일본어 입문자. 홈에서 일본어 입문·초보일 때 카드가 보인다.
- **데이터**: 코드 상수 `src/lib/kana.ts`. AI와 DB를 쓰지 않는다.
  - 히라가나와 가타카나 각각 청음 46자 + 탁음·반탁음 25자 = 71자
  - 글자마다 `{ char, romaji, ko, row }`
- **흐름**: 탭(히라가나/가타카나) → 행 선택(또는 전체) → 플래시카드
  - 앞면: 글자 / 뒷면: `a · 아`
  - [모르겠어요]를 누른 글자는 그 회차 끝에 다시 나온다.
- **기록**: 진행도는 저장하지 않는다. 회차를 마치면 `kana_studied` 이벤트를 남기고 연속 학습일을 갱신한다. 사용량에는 포함하지 않는다.
- **MVP 제외**: 요음, 쓰기 연습, 가나 퀴즈, 글자별 진행도

## 4. 레벨업 테스트

- **응시**: 현재 레벨이 1~4이면 홈의 [레벨업 테스트]로 들어간다. 고수(5)는 테스트가 없다.
- **출제**: 현재 레벨 단어에서 무작위로 **20문제**를 빈칸 채우기로 낸다. 학습과 같은 컴포넌트를 쓴다.
- **채점은 서버에서 한다**
  - 정답은 클라이언트로 보내지 않는다. 보내는 것은 `word_id`, 빈칸 처리한 예문, `example_ko`, 섞은 보기다.
  - 제출: `{ language, from_level, answers: [{ word_id, answer(≤50자) }] }`. 출제 시 언어와 레벨을 고정한다.
  - 서버는 서로 다른 단어 20개가 모두 명시한 언어·from_level(1~4)의 단어인지 확인하고, 학습과 같은 방식(`lib/blank`, 정답 표기와 그대로 비교)으로 채점한다. 결과 저장 RPC는 계정 잠금 후 실제 해당 언어 레벨이 from_level과 다르면 합격 여부와 무관하게 409를 반환한다.
  - 응시 기록은 `level_test_submitted` 이벤트(`{ language, from_level, score, passed }`)로 남긴다.
  - `words`는 읽을 수 있는 테이블이라 완전한 부정 방지는 아니다. 부정행위는 본인 손해일 뿐이라 허용한다.
- **합격** (16/20 이상): `update … where level = from_level`로 레벨을 1 올린다.
  - 같은 시험을 두 번 제출해도 한 번만 오른다.
  - 도중에 다른 탭에서 레벨이 바뀌었으면 409를 돌려준다.
- **불합격**: 점수와 틀린 문제를 보여 준다. 재응시 제한은 없다.
- 사용량에는 포함하지 않고, `user_words`도 바꾸지 않는다. 유효한 제출의 응시 이벤트·레벨 변경·활동일/연속일 갱신은 한 트랜잭션에서 처리한다.

## 5. 플랜, 사용량, 무료 체험

| | Free | Pro |
|---|---|---|
| AI 대화 (턴 수) | 하루 20회 | 하루 150회 |
| 새 단어 | 하루 10개 | 하루 30개 |
| 표시 가격 | 무료 | 월 9,900원 (상수) |

- **세는 방법**
  - 대화: 오늘 생성된 `chat_turns` 행 수 (`pending` 포함)
  - 단어: 오늘 `first_seen_at`이 기록된 `user_words` 행 수
  - 별도 사용량 카운터는 두지 않고, 계정 단위(언어 합산)로 센다. `user_activity_days`는 학습한 날만 기록하며 한도 카운터로 쓰지 않는다.
  - 대화 예약과 단어 신규 저장은 `profiles` 행을 잠근 DB 트랜잭션 안에서 한도를 확인한다. 잠금을 얻은 뒤의 DB 시각으로 날짜·플랜을 한 번 결정한다. 대화의 날짜는 예약 시각(`created_at`), 단어는 저장 시각(`first_seen_at`)에 귀속한다.
  - 기준은 한국 시간 자정이다. 서머타임이 없으므로 UTC+9로 고정 계산한다.
  - 피드백, 복습, 빈칸, 레벨업 테스트, 가나는 세지 않는다.
- **Pro 판단**: `profiles.pro_until > now()`
- **7일 무료 체험**
  - `update profiles set trial_started_at = now, pro_until = now + 7일 where trial_started_at is null`로 처리한다.
  - 바뀐 행이 0개면 409를 돌려준다 (계정당 1번).
- **체험 종료 후**: Free로 돌아간다. Pro 버튼을 누르면 "정식 출시 준비 중"을 보여 주고 `pro_clicked`를 남긴다.
- **한도 도달**: 입력을 막고 체험 또는 Pro 안내를 보여 준다. `limit_reached`는 1장의 서버 기록 규칙을 따른다. 만료된 작업 복구를 위한 재전송 예외는 2장을 따른다.
- **비용 추정** (가정: Haiku 4.5 가격이 입력 100만 토큰당 $1, 출력 $5): 대화 1회 약 $0.004, Free 사용자가 하루 한도를 다 쓰면 약 $0.08

## 6. 아키텍처

### 6-1. 시스템 구성

```
[브라우저] ──▶ [Vercel (icn1): Next.js]
                ├─ 미들웨어: 세션 갱신, 명시된 보호 페이지의 비로그인 요청만 / 로
                ├─ 페이지 (Server Components): 읽기
                └─ /api 라우트: 쓰기 + Claude 호출
                      ▼                        ▼
             [Supabase (서울)]            [Anthropic API]
             Auth(구글) · Postgres        Claude Haiku 4.5

[로컬 스크립트] generate-words → data/words/*.json (검수 후 커밋) → seed-words → Supabase
               metrics-report ← Supabase (지표 분자/분모 출력)
```

**페이지 접근 규칙**
- 공개 경로: `/`, `/privacy`, `/terms`, `/auth/callback`. 로그인 여부와 무관하게 열며 `/`로 재리디렉션하지 않는다.
- 보호 경로: `/onboarding`, `/home`, `/chat` 및 하위 경로, `/words`, `/level-up`, `/kana`, `/account`. 경로 세그먼트 기준으로 구분한다. 비로그인이면 `/`로 보낸다.
- 보호 페이지 중 `/onboarding`을 제외한 페이지는 동의·현재 언어의 레벨을 검사하고, 준비되지 않았으면 `/onboarding`으로 보낸다.
- `/api/**`는 페이지 리디렉션 대상이 아니다. API 래퍼가 JSON 401/403을 반환한다. `/_next/**`, favicon과 정적 파일은 인증 가드에서 제외한다.

### 6-2. 레이어

```
src/app/api/**/route.ts   얇게: route() 래퍼 → use-case 호출 (판단 없는 단일 RPC는 server/db 직접)
src/server/*.ts           use-case: (deps, userId, input) → 결과 | 에러 코드   ← 비즈니스 테스트의 중심
src/server/page.ts        보호 페이지 가드(requireUser·requireReady, React cache)
src/server/db/*.ts        DB 접근 함수: 모두 userId를 받는다. reads.ts는 페이지 읽기(쿠키 client를 인자로, RLS)
src/services/             supabase/{browser,server,admin}.ts, claude/{client,prompts,schemas}.ts, env.ts, apiClient.ts(브라우저 → /api)
src/lib/                  순수 규칙 (I/O 없음. 환경변수 읽기와 fetch도 하지 않는다)
```

- 앱 코드는 모두 `src/` 아래에 둔다. 이 문서에서 `src/`를 생략한 `app/`, `server/`, `services/`, `lib/`, `components/`, `types/`, `test/` 경로도 `src/` 기준이다. `scripts/`, `data/`, `supabase/`는 저장소 루트에 둔다.
- 의존 방향은 app → server → services, lib다. `lib`는 프로젝트 안의 다른 모듈을 import하지 않는다.
- use-case는 `{ db, ai }`를 주입받고, 함수별 결과를 정하는 가짜 구현(`src/test/fakes.ts`)으로 분기와 호출 순서를 테스트한다. RPC 규칙(잠금·한도·상태 전이)을 가짜에 다시 구현하지 않는다. DB 인터페이스는 `beginChatTurn`, `finishChatTurn`, `beginEnd`, `finishEnd`, `saveWordBatch` 같은 트랜잭션 단위로 둔다. 잠금·RLS·원자성은 로컬 DB 통합 테스트로 따로 확인한다.
- 현재 시각은 페이지가 표시용으로만 `lib` 함수에 넘기며, 저장·한도·작업 기한의 실제 판정은 RPC 내부 DB 시각을 사용한다.
- `route()` 래퍼(`server/http.ts`) 하나가 다음을 처리한다: 로그인 확인(401), JSON Content-Type 검사, zod 검증(400), 경로별 동의·온보딩 검사(403), 에러 코드 → HTTP 변환, 예외 → 500. `/end`의 처리 중 응답(202)은 에러로 변환하지 않는다.

### 6-3. 데이터 접근과 보안 (CRITICAL)

| 누가 | 무엇을 | 클라이언트 |
|---|---|---|
| 브라우저 | 로그인, 로그아웃만 | browser client (publishable key) |
| 페이지 | 읽기 | 쿠키 기반 server client. RLS(자기 행 읽기)가 적용된다 |
| route → use-case | 쓰기, Claude 호출 | admin client (secret key). RLS를 우회하므로 반드시 userId로 범위를 제한한다 |

- RLS는 모든 public 테이블에 켜고, "자기 행 읽기" 정책만 둔다 (`words`는 로그인 사용자 전체가 읽을 수 있다). 쓰기 정책은 두지 않는다.
- admin 클라이언트는 `import 'server-only'`로 클라이언트 번들에 들어가지 않게 하고, 함수 안에서 지연 생성한다. 하네스 Stop hook이 매번 `next build`를 돌리는데, env가 없어도 빌드가 깨지지 않게 하기 위해서다.
- **여러 행의 판정과 변경은 DB 함수(RPC) 한 번으로 묶는다.** HTTP로 분리된 조회·변경을 하나의 트랜잭션으로 간주하지 않는다. RPC 구성과 실행 권한은 [Supabase DB 함수 문서](https://supabase.com/docs/guides/database/functions)를 따른다.
  - 계정의 사용량·레벨·활동일·대화 상태를 변경하는 RPC는 먼저 `profiles WHERE id = userId FOR UPDATE`를 잡고, 필요한 세션·학습 행을 잠근다. 모든 경로가 같은 순서를 사용한다.
  - 대화 예약: 만료 작업 복구 + 세션 상태·실패 횟수·한도 확인 + pending와 작업 토큰 저장
  - 대화 확정: 토큰 검증 + 결과 또는 실패 저장 + 토큰 해제 + 필요한 활동일/연속일 갱신
  - 종료: `active → ending` 예약과 `ending → ended` 확정은 각각 짧은 트랜잭션이다. AI 호출 중에는 DB 잠금을 유지하지 않는다.
  - 단어 회차: 기존 단어 제외 + 신규 개수로 한도 확인 + 신규 삽입 + 활동일/연속일 갱신
  - 복습·가나·레벨업 테스트: 결과/이벤트 저장과 활동일/연속일 갱신을 함께 처리한다.
  - 첫 레벨: 동의 확인 후 언어별 PK insert, `current_language` 전환, 최초 `onboarded_at` 설정을 함께 처리한다. 이미 해당 언어의 레벨이 있으면 409이며 다른 언어를 처음 추가하는 것은 허용한다.
  - 체험 시작은 `trial_started_at is null`, 레벨업은 `level = from_level`, 레벨 내리기는 `level > new` 조건을 유지한다. 모두 해당 계정 잠금 규칙을 따른다.
  - 한도 초과 등 예상된 거부는 결과 코드로 반환해 이미 수행한 만료 복구·이벤트 기록을 커밋한다. 예상하지 못한 SQL 오류는 트랜잭션 전체를 롤백한다.
- **RPC 실행 권한**: `SECURITY INVOKER`로 만들고 함수별 `EXECUTE`를 `PUBLIC`, `anon`, `authenticated`에서 회수한 뒤 `service_role`에만 부여한다. 새 함수에도 같은 기본 권한을 적용한다. HTTP에서 검증한 사용자 ID를 서버가 전달하며 body의 userId는 받지 않는다. 내부 helper에도 같은 권한 규칙을 적용한다.
- **세션당 pending 1개를 DB에서도 보장한다.** 작업 토큰과 세션 잠금이 전송·종료 간 경합을 막고, 아래 [부분 UNIQUE 인덱스](https://www.postgresql.org/docs/18/indexes-partial.html)가 여러 pending 생성을 추가로 막는다.
  ```sql
  CREATE UNIQUE INDEX chat_turns_one_pending
    ON public.chat_turns (session_id)
    WHERE status = 'pending';
  ```
  기존 `unique(session_id, turn_no)`도 유지한다. 만료된 pending은 2장의 복구 규칙으로 제거하므로 영구적으로 다음 턴을 막지 않는다.

### 6-4. API

모든 읽기는 페이지에서 한다. 라우트는 쓰기와 Claude 호출을 맡으며, 재요청 시 저장 결과를 반환하는 것은 쓰기 API의 멱등 동작에 포함한다.

| Method | Path | 하는 일 |
|---|---|---|
| GET | `/auth/callback` | 공개 OAuth 콜백. 코드 교환 후 `profiles`가 없으면 생성 |
| POST | `/api/me/consent` | 약관 동의 (`agreed_at`, 최초 시각 유지) |
| PUT | `/api/me/language` | 대상 언어에 레벨이 있을 때 전환 |
| POST | `/api/levels` | 언어의 첫 레벨 설정 + 해당 언어 전환 + 최초 온보딩 완료 시각. 이미 레벨이 있으면 409 |
| PATCH | `/api/levels/[language]` | 레벨 내리기 |
| POST | `/api/chat/sessions` | 만료 작업 복구 + 세션 생성 (Claude 호출 없음) |
| POST | `/api/chat/sessions/[id]/messages` | 대화 1턴 (예약 RPC → Claude → 확정 RPC) |
| POST | `/api/chat/sessions/[id]/end` | 종료 예약·피드백 확정/대체 결과. 완료 200, 처리 중 202, 턴 처리 중 409 |
| POST | `/api/words/batch` | language + items. 신규분만 한도 확인하고 원자적으로 저장, 중복은 200 |
| POST | `/api/words/review` | language + items. 유효한 복습 결과·활동일 저장 |
| POST | `/api/level-up` | 서버 채점, 합격하면 레벨 +1, 응시·활동일 저장 |
| POST | `/api/trial` | 체험 시작 (계정당 1번) |
| POST | `/api/events` | `pro_clicked`, `kana_studied`만 받는다. 가나는 활동일·연속일도 갱신 |

**공통 준비 상태 검사**
- 모든 `/api/**`는 먼저 `getUser()`로 인증한다. 기본은 동의 완료 + 현재 언어에 저장된 레벨이 있는 계정만 허용한다. 요청 언어나 세션 언어를 쓰는 작업은 그 언어의 레벨 존재도 확인한다.
- 예외는 아래 3개뿐이다. 이벤트 이름에 따라 준비 상태 검사를 생략하지 않는다.

| API | 필수 상태 | 예외 이유 |
|---|---|---|
| `POST /api/me/consent` | 로그인 | 최초 동의를 받을 수 있어야 함 |
| `POST /api/levels` | 로그인 + 동의 | 최초 또는 새 언어의 레벨 생성이 가능해야 함 |
| `PUT /api/me/language` | 로그인 + 동의 + 대상 언어 레벨 | 현재 언어가 미설정이어도 이미 설정한 언어로 복구 가능 |

- 조건 부족은 `CONSENT_REQUIRED` 또는 `ONBOARDING_REQUIRED`(403)이며, 거부 시 학습 데이터 변경이나 AI 호출을 하지 않는다. 클라이언트는 `/onboarding`으로 이동한다.
- 민감한 상태 판정은 쓰기 RPC에서도 사용자 행을 잠근 뒤 다시 확인한다. 첫 언어 설정 전의 `profiles.current_language`, `onboarded_at`은 null을 허용한다.

### 6-5. 데이터 모델

| 테이블 | 주요 컬럼 |
|---|---|
| `profiles` | id(=auth.users.id), current_language(nullable), pro_until, trial_started_at, agreed_at, onboarded_at(nullable, 최초 완료 시각), last_study_date, streak, created_at |
| `user_levels` | user_id, language, level(1~5) — PK(user_id, language) |
| `chat_sessions` | id, user_id, language, level, scenario_id, status(active/ending/ended), operation_token(uuid, nullable), operation_expires_at(nullable), feedback_status(none/pending/ready/fallback/skipped), feedback(jsonb), created_at, ended_at |
| `chat_turns` | id, session_id, user_id, turn_no, status(pending/done), user_text, reply, reply_ko, correction(jsonb), created_at — unique(session_id, turn_no) |
| `words` | id(text, 예: `en-1-001`), language, level, rank, word, reading, meaning_ko, example, example_ko, distractors(text[]) — unique(language, level, rank) |
| `user_words` | user_id, word_id, status(known/review), first_seen_at, updated_at — PK(user_id, word_id) |
| `events` | id, user_id, name, props(jsonb), created_at |
| `user_activity_days` | user_id, activity_date(date, 한국 날짜) — PK(user_id, activity_date). 학습 성공이 있는 날만 행이 있다 |

- **인덱스**: `chat_turns(user_id, created_at)`, `user_words(user_id, first_seen_at)`, `events(user_id, name, created_at)`, `chat_sessions(user_id, language, status, created_at)`, `chat_sessions(user_id, operation_expires_at)` 및 위 partial UNIQUE. 활동일은 복합 PK로 사용자별 날짜를 조회한다.
- **상태 제약**: 작업 토큰과 기한은 둘 다 null 또는 둘 다 값이 있어야 한다. `active`는 `feedback_status = none`, `ending`은 토큰이 있고 `feedback_status = pending`, `ended`는 토큰이 없고 `ended_at`과 ready/fallback/skipped 중 하나를 가진다. `ended_at`은 ended일 때만 존재한다. ready/fallback에는 저장된 결과가 있어야 하며 skipped는 feedback이 null이다.
- **활동일**: 학습 성공 RPC가 DB 시각의 한국 날짜로 `insert … on conflict do nothing` 한다. 날짜를 클라이언트가 지정하지 않는다.
- **대화 첫 마디**는 저장하지 않고, `scenario_id`와 언어로 코드에서 다시 만든다.
- **단어 ID**는 생성할 때 부여하고 재사용하지 않는다. seed를 다시 돌려도 학습 기록이 깨지지 않는다.
- **파일 배치**
  - 마이그레이션(`supabase/migrations/`): 스키마, 제약, 인덱스, RLS, RPC 및 실행 권한
  - 단어: `scripts/seed-words.ts`가 upsert한다 (`onConflict: id`)
  - DB 타입: `supabase gen types`로 `types/database.ts`에 생성

### 6-6. Claude 연동

- **구조화 출력**: SDK의 구조화 출력을 쓴다 (`client.messages.create()` + zod 스키마, `output_config.format`). Haiku 4.5가 지원한다. deprecated된 `output_format`은 쓰지 않는다. `stop_reason`을 먼저 본 뒤 첫 text 블록을 zod로 파싱한다. `messages.parse()`는 `stop_reason`을 보기 전에 파싱하다 throw해서 실패 사유를 구분하지 못하므로 쓰지 않는다.
- **실패로 처리하는 경우**(`chat_failed`의 실패 사유): refusal, `max_tokens` 도달, 파싱·스키마 검증 실패(`invalid_output`), 타임아웃, API 오류. env가 없거나 비어 있으면 API를 부르지 않고 재시도 없이 `config`로 실패하며, 키 이름만 에러 로그로 남긴다
- **타임아웃과 재시도**: 호출당 타임아웃 20초. SDK 자동 재시도는 끄고(`maxRetries: 0`) 직접 1번만 재시도한다. 메시지와 종료 라우트 모두 `maxDuration = 60`이며, 재시도 포함 AI 호출 전체 예산은 최대 약 40초다. 두 호출 모두 같은 작업 토큰을 사용한다. 중복 HTTP 요청이나 DB 확정 재시도 때문에 AI 호출을 새로 시작하지 않는다.
- **토큰 상한**: `max_tokens`는 약 1024로 둔다.
- **프롬프트**: 빌더는 순수 함수(`services/claude/prompts.ts`)로 단위 테스트하고, 스키마는 `schemas.ts`에 둔다.
- **대화 기록**: 고정 user 턴("대화를 시작합니다") → 첫 마디 → `done` 턴들 → 이번 입력 순서로 보낸다. `pending` 턴은 넣지 않는다.
- **프롬프트 캐싱은 쓰지 않는다.** 프롬프트가 짧아 최소 캐시 길이에 못 미칠 가능성이 크다. 구현할 때 확인한다.

### 6-8. 출시 최소 요건

- **개인정보처리방침**(`/privacy`)
  - 수집 항목: 구글 이메일·이름, 학습 기록, 대화 내용
  - 목적, 보관 기간, 탈퇴 방법
  - **국외 이전**: 대화 내용이 Anthropic(미국)으로 전송된다. 호스팅 업체(Vercel, Supabase)도 함께 고지한다.
  - 정식 출시 전에 법률 검토를 권장한다.
- **이용약관**(`/terms`): 만 14세 이상만 가입할 수 있다고 명시한다. 온보딩의 필수 체크 1개로 동의를 받고 `agreed_at`에 저장한다.
- **구글 OAuth 동의 화면 "게시"**: 테스트 모드에서는 등록한 사용자만 로그인할 수 있다.
- **회원 탈퇴**: 이메일로 문의를 받아 Supabase 대시보드에서 삭제한다. FK cascade로 기록이 함께 지워진다.
- **비용 안전장치**: Anthropic 지출 한도와 알림, 계정 잠금으로 원자적 사용량 예약, 세션당 작업 하나, 하루 실패 10회 누적 시 새 AI 호출 차단, 입력 300자, 일일 한도. 피드백 생성도 실패 횟수에 포함하며 종료 재요청은 AI를 중복 호출하지 않는다. 출시 전에 Anthropic rate limit 등급도 확인한다.
- **운영 위험**: Supabase 무료 프로젝트는 7일간 요청이 없으면 일시정지된다. 무료 플랜은 백업이 제한적이라 배포 전에 `supabase db dump`를 떠 둔다.

### 6-9. TDD hook에 맞춘 파일 규칙

- TDD guard(`scripts/hooks/tdd-guard.sh`)는 예외(설정·타입·`page`/`layout` 등 Next 파일, 경로에 `test`/`spec`이 들어간 파일)를 뺀 **모든 `.ts(x)`**에 테스트 파일을 요구한다. `route.ts`, 미들웨어, 컴포넌트, use-case, `server/db/*.ts`뿐 아니라 `lib/`, `services/`, `scripts/`도 대상이다. 같은 폴더에 `*.test.ts(x)`를 먼저 만든다.
- `services/supabase/*.ts`와 `services/env.ts`는 env가 없어도 import만으로 throw하지 않고, 호출할 때 검증 에러가 나는지 테스트한다 (Stop hook의 `next build` 안전성).
- `scripts/*.ts`는 입출력을 주입받는 `main(deps)`를 export하고 가짜 deps로 테스트한다 (generate-words: 가짜 AI 응답 → 검증된 JSON, seed-words: JSON → upsert 행, metrics-report: 행 → 분자/분모 출력). 계산 규칙은 `lib/`에 둔다.
- guard는 경로에 `test`가 들어간 파일을 검사하지 않는다. 그래서 레벨업 테스트의 경로는 `/level-up`, `/api/level-up`으로 둔다. `src/test/fakes.ts` 같은 테스트 보조 파일은 이 규칙 덕분에 통과한다.
- DB 접근 파일의 `server/db/*.test.ts`는 실제 DB 통합 테스트로 작성한다. Vitest 기본 실행에서 이 경로를 제외하고 `test:db`에서 포함한다. Supabase 쿼리 체인을 mock하거나 hook 통과만을 위한 빈 테스트를 만들지 않는다.
- 정적 UI는 `page.tsx`/`layout.tsx`에 둔다 (hook이 검사하지 않음). 컴포넌트는 꼭 필요한 것만 만든다.
  - 화면 단위: `OnboardingFlow`, `ScenarioPicker`, `ChatRoom`, `ChatFeedback`, `WordSession`, `LevelTestRunner`, `KanaDeck`
  - 공용: `Flashcard`, `BlankQuiz`, `Furigana`, `LanguageSheet`(상단 언어·레벨 메뉴), `AppNav`, `UsageCard`, `Dialog`, `Toast`, `WaitingDots`, `GoogleLoginButton`, `TrialButton`(체험 시작), `ProButton`(Pro 클릭·준비 중 모달), `LimitNotice`(한도 도달 안내), `LogoutButton`. 만든 이유는 `docs/spec/ui.md` "공용 React 컴포넌트와 이유"에 있다
  - 입력·API 호출이 있는 부분만 Client Component로 만든다. 페이지의 분기 규칙은 테스트할 수 있게 `lib/`(예: `today`, `readiness`, `onboarding`)에 둔다.
  - 페이지 읽기는 `server/db/reads.ts`에 두고 `test:db`로 실제 RLS와 함께 검증한다. 운영자 정보는 설정 파일 `src/site.config.ts`에 둔다.
- Vitest 설정에서 `server-only`를 빈 모듈로 alias한다.

### 6-10. 에러 코드

응답 형식은 `{ code, message }`이고, `message`는 사용자에게 보여 줄 한국어 문구다.

| code | HTTP | 언제 | 클라이언트 동작 |
|---|---|---|---|
| `UNAUTHORIZED` | 401 | 로그인 안 됨·만료 | `/`로 이동 |
| `CONSENT_REQUIRED` | 403 | 약관 동의 없음 | `/onboarding` 동의 단계로 이동 |
| `ONBOARDING_REQUIRED` | 403 | 필요한 언어·레벨 미설정 | `/onboarding` 레벨 단계로 이동 |
| `INVALID_INPUT` | 400 | zod 실패, 다른 레벨의 상황, 잘못된 시험 제출 | 문구 표시 |
| `NOT_FOUND` | 404 | 없거나 남의 리소스 | 홈으로 이동 |
| `LIMIT_REACHED` | 429 | 플랜 한도 초과 | 체험 또는 Pro 안내 |
| `AI_FAILURE_LIMIT` | 429 | 하루 실패 10회 | 대화 입력 비활성화 |
| `AI_UNAVAILABLE` | 503 | 메시지 생성 실패 | 입력 유지, 다시 보내기 (종료 피드백 실패는 대체 결과로 200) |
| `SESSION_FULL` | 409 | 20턴 초과 | `/end` 호출 |
| `CONFLICT` | 409 | 진행 중인 턴, 종료 중/끝난 세션에 전송, 만료·교체된 작업 토큰, 레벨이 이미 있음·바뀜, 체험 사용함 | 입력을 보존하고 상태를 새로 읽음. 전송/종료를 자동 반복하지 않고 필요한 재시도 버튼 표시 |
| `INTERNAL` | 500 | 예상하지 못한 예외 (로그 남김) | "잠시 후 다시 시도" |

- 클라이언트는 fetch 래퍼 하나(`services/apiClient`)에서 처리한다. `/end`의 202는 성공한 처리 중 응답으로 구분해 `retryAfterSeconds` 이후 다시 확인한다.
  - 401은 `/`로, 403(`CONSENT_REQUIRED`·`ONBOARDING_REQUIRED`)은 `/onboarding`으로 래퍼가 이동시킨다.
  - `fetch` 자체가 실패하면(네트워크 끊김) 클라이언트 전용 코드 `NETWORK`로 돌려준다. 503 문구("턴은 차감되지 않았어요")를 네트워크 오류에 쓰지 않기 위해서다. JSON이 아닌 응답은 `INTERNAL`로 본다.
- 네트워크 오류는 해당 작업의 입력·결과를 보존한다. 메시지는 수동 재전송, 단어 저장과 `/end`는 재시도 버튼으로 확인한다. 단어 중복 저장은 200이며 활동일·사용량을 다시 늘리지 않는다.
- 페이지에는 `error.tsx`와 `not-found.tsx`를 둔다. Supabase 장애는 페이지 에러로 보여 준다.
- Anthropic이 장애여도 단어, 가나, 레벨업 테스트는 계속 쓸 수 있다.

## 7. 테스트, MVP 제외

**테스트 (TDD, Vitest)**
- **`lib/` 단위 테스트**
  - plan: Pro 여부, 한도, 체험 가능 여부
  - usage: 한국 시간 자정 경계, 예약일과 성공일이 다른 턴
  - streak: 오늘/어제/그 외 갱신 규칙, 표시 규칙
  - furigana: 파싱, 깨진 표기는 일반 텍스트로
  - blank: `{{ }}` 파싱, 정답 추출, 보기 섞기, 정답 판정
  - text: 글자 수
  - wordBatch: 회차 크기(남은 단어 0/1~9 포함), known/review 결정, 신규분 계산
  - levelTest: 20개 검증, 16/20 경계
  - levels: 후리가나·번역·한국어 입력·레벨업·가나 표시 경계 / today: 목표 진행·소진·남은 할 일 수 / readiness: 요구 수준별 동의·레벨 판정 / errors: 코드별 HTTP 상태
  - metrics: D1/D7 한국 날짜, 관찰 완료 분모, 운영 계정 제외, 최소 표본 미달 판단 보류, 유효한 세션(성공 턴 3개 이상, 종료 여부 무관), 한도 도달 `feature`별 분리, Pro 관심은 경로 무관 체험 시작자
- **services**: 프롬프트 빌더, 응답 스키마, 재시도 1번과 호출 예산, refusal과 `max_tokens`는 실패로 처리
- **use-case** (가짜 db와 ai 주입; 실제 경합 증명은 아래 DB 통합 테스트)
  - 대화: 정상, 한도·20턴·실패 10회 차단, 예약 거부 시 AI 미호출, 실패 확정 후 예약 반환, 만료·교체된 토큰의 결과 폐기
  - `/end`: 0턴 skipped, 이미 종료된 결과 재사용, 처리 중 202, 턴 진행 중 409, AI 실패/실패 한도 시 fallback, DB 확정 재시도 시 AI 미호출
  - 보안: 남의 세션 404, 미동의·미온보딩 API 403와 AI/학습 변경 없음, 초기 설정 API 예외
  - 레벨: API로 올리기는 거부, 합격 시에만 +1, 도중에 레벨이 바뀌면 409, 첫 완료 시각 유지
  - 체험: 두 번째 요청 거부
  - 단어: 한도 0에서 기존 10개 재전송 성공, 기존+신규 혼합은 신규만 검사, 초과 신규분 전부 거부, 전부 중복이면 다음 날에도 활동일·연속일 변경 없음
  - 학습: 복습·가나·테스트만 한 날도 활동일 기록
  - 지표: 한도를 채우는 마지막 성공 저장에도 limit_reached 기록, 초과 요청 없이도 체험 전환 분모에 포함, 단어 재전송은 이벤트 추가 없음
- **DB 통합 테스트 (`npm run test:db`, 로컬 Supabase)**
  - supabase-js로 RPC를 호출한다. RPC는 커밋한 뒤 응답하므로 요청 순서는 순차 호출로, 동시 실행은 `Promise.all`(요청마다 별도 연결·트랜잭션)로 만든다. 처리 기한 만료는 `operation_expires_at`을 과거로 바꿔 재현한다. AI 호출 단계는 예약 RPC와 확정 RPC 사이의 간격으로 대신하며 외부 AI를 부르지 않는다.
  - A의 pending 커밋 후 완료 전에 B가 같은 세션으로 전송: B는 409, pending은 정확히 1개. turn_no UNIQUE만으로 통과하는 테스트를 만들지 않는다.
  - 같은 계정의 다른 세션에서 한도 1회 남기고 동시 예약: 하나만 허용
  - 턴 예약과 종료가 경합: 먼저 예약한 상태에 따라 다른 요청은 거부. 동시 종료는 작업 하나만 예약
  - pending 만료 복구·ending 만료 fallback·늦게 도착한 성공/실패가 새 작업과 종료 결과를 변경하지 않음
  - 실패 확정과 복구 동시 실행 시 예약 반환·실패 이벤트가 한 번만 반영됨
  - 서로 다른 단어 묶음·두 언어의 회차 동시 저장: 총 신규분이 한도를 넘지 않음. 같은 회차 동시 재전송은 한 번만 삽입
  - 같은 날 학습 동시 저장에서 활동일 행은 하나만 남음, 결과 저장과 활동일·연속일 갱신의 동시 커밋·롤백
  - anon/authenticated의 쓰기·RPC 호출 거부, 타인 행 RLS 읽기 거부, service_role RPC에서도 타인 세션 변경 거부
- **route / 페이지 접근**
  - `route()` 래퍼: 401, 403, 400, 에러 매핑, 500, JSON이 아닌 요청 거부, 202 정상 처리
  - 미들웨어: 비로그인 `/`, `/privacy`, `/terms`, 콜백은 통과, `/home`은 이동, `/api/**`는 리디렉션하지 않음, 정적 파일 제외
  - 페이지 준비 상태: 미동의 사용자의 보호 페이지 → 온보딩, 온보딩·공개 페이지에서 이동 루프 없음
  - 각 `route.test.ts`는 연결과 해당 경로 준비 상태 확인
- **컴포넌트**
  - `Furigana`의 HTML 비주입·깨진 표기 처리, 대화 입력의 IME Enter
  - 종료 202 표시·재확인·fallback에서 저장된 턴 교정 확인
  - 레벨 1~4/5 단어 소진 분기, 오답 0개, 소진 뒤 미완료 10개 목표/잘못된 체험 유도 없음, 레벨·언어 변경 후 일반 화면 복귀
  - 대화 입력은 표시된 남은 횟수가 0이어도 막지 않고 429 응답 뒤에만 막음
- **데이터 검증**
