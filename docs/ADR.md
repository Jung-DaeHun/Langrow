# Architecture Decision Records

## 철학
수요 검증이 MVP의 유일한 목표다. 검증에 필요 없거나 없어도 사용자가 불편하지 않은 것은 만들지 않는다. 대신 돈(AI 비용)과 데이터 무결성(한도, 레벨, 지표)에 관한 규칙은 DB 트랜잭션으로 확실히 지킨다. 상세 동작은 `docs/spec/`에 있다.

---

### ADR-001: Next.js App Router + Supabase + Vercel
**결정**: Next.js(App Router, TypeScript strict, Tailwind)를 Vercel(icn1)에, Supabase(Auth 구글·Postgres·RLS, 서울)를 DB로 쓴다.
**이유**: 한 저장소에서 페이지와 API를 함께 만들고, 인증·RLS를 직접 구현하지 않는다. 사용자와 같은 지역이다.
**트레이드오프**: Supabase 무료 플랜은 7일 무요청 시 일시정지되고 백업이 제한적이다. 배포 전 `supabase db dump`로 대비한다.

### ADR-002: use-case 레이어(`src/server/`)와 의존성 주입
**결정**: route는 얇게 두고, 비즈니스 규칙은 `{ db, ai }`를 주입받는 use-case에 둔다. 판단 없이 RPC 하나만 부르는 API는 route가 `server/db`를 바로 부른다. DB 인터페이스는 트랜잭션 단위다.
**이유**: 분기·호출 순서를 Docker 없이 가짜 구현으로 빠르게 테스트하고, Stop hook(lint·build·test)을 통과시킨다.
**트레이드오프**: 잠금·RLS·원자성은 가짜로 증명할 수 없어서 `test:db`(로컬 Supabase) 통합 테스트를 따로 유지한다.

### ADR-003: 여러 행의 판정은 RPC 트랜잭션 + 계정 잠금
**결정**: 한도·세션 상태·레벨·활동일·연속일의 판정과 변경은 RPC 하나로 묶고, 먼저 `profiles` 행을 `FOR UPDATE`로 잠근다. 모든 경로가 같은 잠금 순서를 쓴다.
**이유**: 두 탭·두 언어의 동시 요청이 한도를 넘거나 연속일을 덮어쓰지 않게 한다. HTTP로 분리된 조회·변경은 원자적이지 않다.
**트레이드오프**: 로직 일부가 SQL 함수로 가고, 마이그레이션과 실행 권한 관리가 필요하다.

### ADR-004: 대화 턴은 예약 → AI → 확정, 작업 토큰 90초
**결정**: 예약 RPC가 pending 턴과 세션 작업 토큰(90초 기한)을 만들고 커밋한 뒤 잠금 밖에서 Claude를 부른다. 확정 RPC는 토큰·기한이 맞을 때만 저장한다. 세션당 pending 1개를 partial UNIQUE로도 보장한다. 정리용 cron 없이 다음 요청에서 만료 작업을 복구한다.
**이유**: AI 호출(최대 약 40초) 동안 DB를 잠그지 않으면서 동시 전송·늦게 도착한 응답이 한도와 결과를 망치지 않게 한다.
**트레이드오프**: 상태가 늘어난다. 네트워크 끊김 후 같은 메시지 재전송 중복은 감수한다(멱등 키 없음).

### ADR-005: 세션 종료는 active → ending → ended, 실패 시 대체 결과
**결정**: `/end`는 멱등이다. `ending` 예약을 얻은 요청만 Claude로 피드백을 만들고, 처리 중 재요청은 202, 실패·기한 만료는 고정 대체 결과(fallback)로 끝낸다. 0턴 세션은 AI 없이 skipped로 끝낸다.
**이유**: 동시·반복 종료 요청이 AI를 중복 호출하지 않게 한다. `ending` 제거도 검토했지만, 같은 방어를 하려면 결국 비슷한 상태가 필요해서 유지했다.
**트레이드오프**: 202 재확인 처리가 클라이언트와 래퍼에 들어간다. 대체 결과 확정 후 피드백 재생성은 하지 않는다.

### ADR-006: Claude Haiku 4.5 + 구조화 출력, 스트리밍·캐싱 없음
**결정**: 기본 모델은 `claude-haiku-4-5-20251001`(환경변수로 변경). `client.messages.create()` + 구조화 출력(`output_config.format`)으로 받고, `stop_reason`을 먼저 본 뒤 zod로 `{ reply, reply_ko, correction }`을 파싱한다. SDK 재시도는 끄고 직접 1번 재시도한다.
**이유**: 대화 1회 약 $0.004로 비용이 낮다. 프롬프트가 Haiku 4.5의 캐시 최소 길이(4096토큰)에 못 미칠 가능성이 크다.
**트레이드오프**: 응답을 한 번에 받아 체감 대기 시간이 있다. 일본어 교정 품질은 출시 전에 샘플로 확인한다.
**변경**: 모델은 ADR-012에서 Claude Sonnet 5.5로 바꿨다.

### ADR-007: 사용량은 원본 행으로 계산, 한도는 계정 단위
**결정**: 별도 카운터 없이 오늘 `chat_turns`(pending 포함)와 `first_seen_at`이 오늘인 `user_words`를 센다. 언어를 합산하고 한국 자정(UTC+9)에 초기화한다.
**이유**: 카운터와 원본이 어긋날 일이 없다. pending을 포함해 동시 예약도 한도를 넘지 않는다.
**트레이드오프**: 만료된 pending이 복구 전까지 표시 사용량에 남는다. 그래서 입력은 서버 429 뒤에만 막는다.

### ADR-008: 단어는 미리 생성, 빈칸은 4지선다, 레벨업은 서버 채점
**결정**: 언어 × 레벨 200개를 스크립트로 생성해 검수 후 커밋하고 seed한다. 빈칸은 모든 레벨 4지선다로 문자열을 그대로 비교한다. 레벨업 테스트는 서버가 채점한다.
**이유**: 학습 중 AI 비용이 없고, 정규화·직접 입력 채점이 필요 없다. 레벨 변경은 어차피 서버에서 해야 한다. 단어를 레벨당 100개로 줄이는 안과 레벨업 테스트를 클라이언트에서 채점하는 안도 검토했지만 적용하지 않았다.
**트레이드오프**: `words`는 읽을 수 있는 테이블이라 부정은 완전히 막지 못한다(본인 손해로 허용). 단어 2,000개 검수 부담이 있다.
**변경**: 빈칸 정답 설명은 ADR-013에서 처음 요청 때 AI로 만들어 저장하기로 했다. 학습 자체에는 여전히 AI 비용이 없다.

### ADR-009: 지표는 서버 기록만, 로컬 스크립트로 계산
**결정**: 이벤트는 다른 테이블로 알 수 없는 것만 남긴다. 학습한 날은 `user_activity_days`에 남기고, 방문 추적은 하지 않는다. 유효한 대화 세션은 성공 턴 3개 이상(종료 무관). `scripts/metrics-report.ts`가 `lib/metrics`로 분자/분모를 계산한다.
**이유**: 판단 기준은 서버가 기록한 학습만 쓴다. 클라이언트 방문 기록은 누락·조작 가능성이 있고 구현 비용이 크다.
**트레이드오프**: 가입 전 퍼널과 단순 재방문율은 볼 수 없다. 대시보드가 없어서 지표는 로컬에서 실행해 확인한다.

### ADR-010: 동의·준비 상태는 페이지와 API 모두에서 검사
**결정**: 온보딩 필수 체크 1개로 동의를 받는다. 보호 페이지는 `/onboarding`으로 보내고, API는 래퍼와 쓰기 RPC에서 403(`CONSENT_REQUIRED`, `ONBOARDING_REQUIRED`)을 반환한다. 예외는 consent·levels·language 3개뿐이다.
**이유**: 페이지 이동만으로는 API 직접 호출을 막을 수 없다.
**트레이드오프**: 모든 쓰기 경로에 준비 상태 검사가 들어간다.

### ADR-011: 환경은 로컬 Docker + 클라우드 prod 1개
**결정**: 로컬은 Supabase CLI(Docker), 운영은 Supabase 클라우드 1개와 Vercel Production. Vercel Preview는 끈다.
**이유**: dev DB가 없으므로 Preview가 prod DB를 써서 지표를 오염시키는 것을 막는다.
**트레이드오프**: 배포 전 검증은 로컬에서만 한다.

### ADR-012: 대화 모델을 Claude Sonnet 5.5(effort low)로 변경
**결정**: 기본 모델을 `claude-sonnet-5-5`로 바꾸고 `output_config.effort = "low"`, `max_tokens` 4096으로 부른다. thinking은 지정하지 않는다(adaptive). 구조화 출력·재시도·실패 처리는 ADR-006 그대로다.
**이유**: 2026-10-08에 일본어 13문장(레벨 1~5)을 같은 프롬프트로 비교했다. Haiku 4.5는 후리가나 누락 4건과 깨진 표기 1건, 교정 누락(`熱もあるです`, `遅くしても`), 이름 표기 오류가 있었다. Sonnet 5.5는 교정 대신 다음 대사를 제안한 1건 말고는 문제가 없었고, 응답 시간은 평균 약 3.7초로 Haiku와 비슷했다. `low`에서는 13문장 모두 thinking 없이 답해 thinking을 끈 설정과 비용이 같았다.
**트레이드오프**: 턴당 비용이 약 2배다(일본어 약 $0.0036 → $0.0074). 지금은 결제가 없어 검증 기간 비용만 늘지만, Pro(월 9,900원, 하루 150턴)는 많이 쓰는 사용자에게 적자가 날 수 있어 결제 전에 프롬프트 캐싱과 Pro 한도를 다시 본다. effort를 받지 않는 모델(Haiku 4.5)로 env를 바꾸면 모든 호출이 실패한다.

### ADR-013: 빈칸 정답 설명은 처음 요청 때 AI로 만들고 (단어, 보기)별로 저장해 재사용한다
**결정**: 단어 학습 빈칸(채점 뒤)과 오답 복습 카드 뒷면에서 요청하면 `POST /api/words/explain`이 설명을 준다. 예약 RPC가 계정 잠금 안에서 Free 하루 10회를 확인하고 `word_explained` 행을 남긴다. 단어 해시가 같은 저장본(`word_explanations`)이 있으면 그것을 주고, 없으면 실패 10회를 확인한 뒤 대화와 같은 모델로 만들어 저장한다. 실패하면 예약 행을 지우고 `chat_failed`를 남긴다. 저장본도 Free 한도에 들어가며 Pro는 무제한이다. 한도 거부는 `limit_reached`로 남기지 않는다.
**이유**: 설명은 사용자와 무관하게 DB 값만으로 정해져 조합이 많아야 약 1만 개다. 저장하면 전체 생성 비용의 상한이 약 $40으로 정해지고, 저장본은 바로 응답하며, 잘못된 설명을 찾아 지울 수 있다. 단어 데이터에 미리 만들면 2,000개 생성·검수·seed가 필요하고 고른 오답에 맞춘 설명을 줄 수 없다. 단어 해시를 같이 저장해 사람 검수 뒤 고친 단어의 옛 설명을 쓰지 않는다. `limit_reached`를 남기면 체험 전환 지표의 `feature` 정의가 바뀐다.
**트레이드오프**: 처음 만든 설명은 사람이 검수하지 않은 채로 여러 사용자에게 반복해 보인다. 프롬프트나 모델을 바꾸면 저장본을 직접 지워야 새 설명이 나온다. 동시에 처음 요청한 두 사람은 AI를 두 번 부를 수 있다. 같은 단어를 다시 풀면 저장본이어도 다시 센다.

### ADR-014: 음성은 단어·예문·가나를 Azure로 미리 만들어 저장소에 커밋하고, 대화 문장은 브라우저 음성으로 읽는다
**결정**: 로컬 스크립트(`scripts/generate-audio.ts`)가 Azure Speech 무료 등급(F0)으로 단어·예문·가나 mp3 약 4,071개를 만들어 `public/audio/female/`에 커밋하고, Vercel이 정적 파일로 제공한다. 지금은 여성 음성(Ava·Nanami)만 만들고, 경로의 첫 폴더를 음성 종류로 두어 나중에 남성 음성(`male/`, 계정 설정)을 파일 이동 없이 추가한다. 일본어는 데이터의 후리가나를 SSML `<sub alias>`로 넘겨 읽기를 지정한다. `data/audio-manifest.json`의 SSML 해시로 바뀐 것만 다시 만들고, `npm run test`가 모든 단어·가나의 파일과 해시를 확인한다. 대화 문장(AI 말풍선·교정)은 브라우저 `speechSynthesis`로 읽고, 학습 언어 음성이 없는 기기에서는 버튼을 숨긴다. 재생은 누를 때만 하고 이벤트를 남기지 않는다(`docs/spec/audio.md`).
**이유**: 무료가 조건이었다. 단어·예문·가나는 사용자와 무관한 고정 데이터라 한 번 만들면 끝나고(과금 기준 약 14.3만 자, 무료 한도 월 50만 자), 모든 사용자가 같은 뉴럴 음성을 듣는다. 브라우저 음성만 쓰면 기기마다 품질이 다르고 일본어 한자 읽기를 지정할 수 없다. Azure를 Google보다 고른 것은 무료 한도가 공식 문서로 확인됐고 SSML 읽기 지정을 오래 지원해서다(Google Chirp 3 HD는 2025-10부터 일부 태그만 지원). Supabase Storage 대신 저장소에 커밋한 것은 단어 JSON과 같은 커밋에서 검수·배포되고, 운영에 따로 올리는 단계가 없고, 빠진 파일을 오프라인 테스트로 잡을 수 있어서다. 대화 문장은 매번 달라 미리 만들 수 없고, 서버에서 만들면 재생마다 비용이 든다.
**트레이드오프**: 저장소가 약 50MB 커지고, 단어를 고쳐 다시 만들 때마다 바이너리 이력이 쌓인다. 단어를 고치려면 Azure 키가 있어야 테스트가 통과한다. F0는 분당 20회라 첫 생성에 약 3.4시간이 걸린다. Azure 무료 체험 구독은 30일 뒤 종량제로 올려야 계속 쓸 수 있다(F0는 과금하지 않는다). 대화 음성은 기기마다 품질이 다르고 한자를 잘못 읽을 수 있다. Azure 이용 규정에 따라 합성 음성임을 화면에 알린다.

### ADR-015: 일본어 한글 발음은 AI가 만든다 (대화는 턴마다, 단어는 미리 만들어 저장)
**결정**: 일본어 입문~중급에서 대화 말풍선·교정 문장·단어 카드·빈칸 채점 뒤 예문 아래에 한글 발음을 보여 준다. 대화는 일본어 입문~중급 턴의 Claude 응답에 `reply_pron_ko`·`corrected_pron_ko`를 더해 `chat_turns`에 저장한다. 단어는 `generate-words`·`generate-pronunciation`으로 `pron_ko`·`example_pron_ko`를 만들어 단어 JSON에 커밋하고 seed한다. 첫 마디는 `scenarios.ts`에 둔다. 표기 규칙은 하나(`docs/spec/chat.md` "한글 발음")이고, 발음이 검사에 맞지 않으면 대화에서는 그 줄만 숨긴다.
**이유**: 가나를 글자마다 한글로 바꾸는 순수 함수는 비용이 없지만, 조사 は·へ를 "하"·"헤"로(こんにちは → 콘니치하) 쓰고 장음을 구분하지 못한다. 조사 は는 거의 모든 문장에 나오므로 입문자에게 틀린 발음을 가르치게 된다. 단어 발음은 사용자와 무관한 고정 데이터라 한 번 만들어 저장하면 끝나고(약 $1~2), 사람 검수 대상에 함께 들어간다. 대화 문장은 매번 달라 턴마다 만들 수밖에 없다.
**트레이드오프**: 일본어 입문~중급 턴의 비용이 약 3분의 1 늘어난다(턴당 약 $0.0022~0.0024, 2026-10-14 실측. 대부분 매 턴 보내는 표기 규칙 입력 약 940토큰이라 프롬프트 캐싱으로 줄일 수 있다. 규칙의 오류 예 약 220토큰은 검수에서 틀렸던 단어의 재생성 오류를 절반으로 줄여서 넣었다). DB 컬럼 3개(`chat_turns` 1개, `words` 2개)와 `finish_chat_turn` 인자가 늘어 운영 DB에 마이그레이션과 seed를 다시 해야 한다. AI가 만든 발음은 틀릴 수 있고, 단어를 고치면 발음도 다시 만들어야 한다. 기능을 넣기 전의 대화 턴에는 발음이 없다.

### ADR-016: 한국어 입력과 일본어 후리가나를 모든 레벨에 둔다 (가타카나 읽기는 코드가 단다)
**결정**: 한국어로 입력하면 학습 언어로 옮긴 문장을 보여 주는 규칙을 입문·초보에서 모든 레벨로 넓힌다. 일본어 후리가나는 입문~중급의 한자에서 모든 레벨의 한자와 가타카나로 넓힌다(가나 익히기 카드 제외). 한자 읽기는 지금처럼 AI·데이터의 `[漢字|かな]` 표기를 쓰고, 가타카나 읽기는 화면에 그릴 때 코드가 같은 소리의 히라가나로 바꿔 단다. 대화방 맨 위에 한국어 입력과 번역 보기를 알리는 안내 줄을 두고 입력창 placeholder는 지운다. 한글 발음은 입문~중급 그대로다.
**이유**: 2026-10-17 운영 확인에서 영어 상급으로 한국어를 입력했더니 바꾼 문장이 나오지 않았다. 말이 막힐 때 한국어로 쓰고 바로 배우는 흐름은 레벨과 상관없이 필요하다고 운영자가 정했다. 후리가나도 운영자가 모든 레벨에서 보이기로 정했다. 가타카나는 글자마다 히라가나가 하나로 정해져서 AI 없이 틀리지 않고 비용도 없다. 음성 SSML은 한자 표기만 계속 써서 이미 만든 음성 파일을 다시 만들지 않는다.
**트레이드오프**: 상급·고수에서 한자를 읽기 없이 읽는 연습이 없어진다. 상급·고수 일본어 턴은 후리가나 표기만큼 출력 토큰이 늘고, 한국어 입력 턴은 교정이 늘 붙는다. 이미 저장된 상급·고수 일본어 턴에는 한자 표기가 없어 읽기 없이 보인다(가타카나 읽기는 붙는다).

### ADR-017: Claude API 오류 로그에 Anthropic 에러 문장까지 남긴다
**결정**: 타임아웃이 아닌 Claude API 오류는 시도마다 상태·에러 종류·요청 ID·SDK 에러 문장(300자까지)을 서버 로그에 남긴다. 프롬프트·사용자 입력·AI 응답은 남기지 않는다.
**이유**: 2026-10-17 운영에서 지출 한도 초과(400 `invalid_request_error`)로 대화가 실패했는데 로그에는 `api_error`만 있어 원인을 알 수 없었다. 상태와 종류만으로는 지출 한도 초과와 다른 요청 오류를 구분할 수 없다.
**트레이드오프**: 에러 문장은 Anthropic이 만든다. 지금은 잔액·형식 같은 내용이고 사용자 대화가 들어가지 않지만, 앞으로도 그렇다고 보장할 수는 없다. 운영자가 이를 알고 문장을 남기기로 정했다.

### ADR-018: 문장 뜯어보기는 턴마다 AI가 함께 만들어 저장한다
**결정**: AI 말풍선과 교정 문장의 의미 조각별 한국어 뜻(`reply_breakdown`, `correction.breakdown`)을 모든 언어·레벨의 턴 응답에 더해 받고, 검사(조각을 이으면 문장과 같은지)를 통과한 것만 `chat_turns`에 저장한다. 화면에서는 [문장 뜯어보기]로 열고 닫는다. 첫 마디는 `scenarios.ts`에 AI 초안을 사람이 검수해 둔다.
**이유**: 2026-10-17 운영 확인에서 사용자가 번역·교정 설명이 문장 전체를 한 번에 옮겨 어느 부분이 어떤 뜻인지 모르겠다고 했다. 처음 열 때 따로 부르는 방식(열어 본 문장만 약 $0.003)과 비교해 운영자가 턴마다 만들기를 골랐다. 열면 기다리지 않고 바로 보이며, 따로 부르는 호출의 실패·재시도·사용량 규칙을 새로 만들지 않아도 된다.
**트레이드오프**: 열어 보지 않는 턴에도 비용이 든다(턴당 약 $0.002~0.003 추정, 일본어 턴 비용의 약 4분의 1~3분의 1). 출력이 늘어 턴 응답이 약 1~3초 늦어질 수 있다(추정, 지금 평균 약 3.7초). 운영자가 이 정도는 괜찮다고 정했다. 모델이 조각을 빼거나 형태를 바꾸면 그 문장은 뜯어보기 없이 보인다. DB 컬럼 1개와 `finish_chat_turn` 인자가 늘어 운영 DB에 마이그레이션을 적용해야 한다. 기능을 넣기 전의 턴에는 뜯어보기가 없다.
**변경**: ADR-027에서 처음 열 때 그 문장만 만들어 저장하기로 바꿨다(2026-10-20 실측에서 턴 출력의 54%).

### ADR-019: 상황을 레벨당 7개로 늘리고, 위 레벨은 잠그고, Free는 레벨마다 3개, 모두 입문에서 시작한다
**결정**: 상황을 레벨당 4개에서 7개(총 35개)로 늘린다. 지금 레벨 이하의 상황을 열고, 아래 레벨 상황도 AI는 지금 레벨 난이도로 말한다(세션 레벨 = 지금 레벨). 위 레벨 상황은 제목까지 보여 주되 잠그고 레벨업 테스트로 안내한다. Free는 레벨마다 앞 3개(기존 순서), 4~7번째는 체험·Pro 상황이다. Pro 상황은 화면과 함께 세션 생성 RPC가 DB 시각의 플랜으로 막고, 새 세션만 막는다. 온보딩의 레벨 선택 단계를 없애 모든 언어를 입문에서 시작한다.
**이유**: 레벨당 4개면 하루 1세션 사용자가 D7 전에 같은 상황을 되풀이한다. 첫 마디가 고정이라 더 똑같이 느껴진다. 7개면 7일 동안 겹치지 않는다. 상황은 코드 상수라 늘려도 운영비는 그대로이고 비용은 검수 시간뿐이다. 위 레벨 잠금은 레벨업 동기를, Pro 표시는 Pro의 가치를 보여 준다. 레벨업으로 상황이 열리는 구조에서 처음부터 높은 레벨을 고르면 잠금의 의미가 없어서 모두 입문에서 시작한다. 2026-10-18 운영자와 brainstorming으로 정했다.
**트레이드오프**: Free 사용자는 입문에서 상황 3개로 시작해(전에는 4개) 레벨업 전이면 4일째부터 같은 상황을 되풀이한다. 7개로 겹치지 않는 것은 체험·Pro 사용자이고, Free에게는 되풀이가 체험으로 가는 계기가 된다. 운영자가 이 구분을 정했다. 이미 아는 사용자는 원하는 레벨까지 레벨업 테스트를 여러 번 봐야 한다(배치 테스트는 MVP 제외). 첫 화면이 쉬운 내용이라 상급 사용자가 이탈할 수 있어, 온보딩과 첫 홈에 "이미 아는 단계는 레벨업 테스트로 바로 올릴 수 있어요"를 둔다. 단어도 입문부터 시작한다. 새 상황 15개(첫 마디 30개)의 초안과 사람 검수가 필요하다. Pro 상황 때문에 체험을 시작했는지는 기록하지 않는다(새 이벤트 없음). "한도 도달 전 체험 시작"을 참고 지표로만 본다. `create_chat_session`에 인자가 하나 늘어 운영 DB에 마이그레이션을 먼저 적용해야 한다.

### ADR-020: Pro 하루 대화 한도를 150턴에서 50턴으로 낮춘다
**결정**: Pro(체험 포함)의 하루 AI 대화 턴을 150에서 50으로 낮춘다. Free 20턴, Pro 새 단어 30개, 표시 가격 월 9,900원은 그대로다. 판정하는 DB 함수 `chat_turn_limit`과 화면이 쓰는 `PLAN_LIMITS`를 함께 바꾼다.
**이유**: Pro 사용자가 매일 150턴을 다 쓰면 월 약 $36(한글 발음·문장 뜯어보기를 더하면 약 $58)으로, 부가세·카드 수수료를 뺀 9,900원(약 $6)을 크게 넘는다(ADR-012 트레이드오프, `usage.md` "비용 추정"). 50턴은 하루 세션 2개 반(세션당 최대 20턴)이다. 2026-10-19 운영자가 정했다.
**트레이드오프**: 매일 한도를 다 쓰면 여전히 월 약 $12(한글 발음·문장 뜯어보기를 더하면 약 $20)로 표시 가격보다 커서, 결제를 붙이기 전에 프롬프트 캐싱을 적용해 실측하고 가격과 한도를 다시 본다. Free와의 대화량 차이가 7.5배에서 2.5배로 줄어 대화량만으로는 Pro의 가치가 덜 보인다. 바뀐 날 이미 50턴 넘게 쓴 체험 사용자는 그날 바로 막힌다. 약관의 Pro 한도 문구도 바뀐다. 함수 본문만 바뀌어 옛 코드와 함께 돌아가지만, 운영 DB에 마이그레이션을 먼저 적용한다.

### ADR-021: Pro 표시 가격을 월 9,900원에서 14,900원으로 올린다
**결정**: Pro 표시 가격(`PRO_PRICE_KRW`)을 월 14,900원으로 바꾼다. 결제는 여전히 없고, 랜딩·계정·약관·한도 안내에 보이는 값만 바뀐다. 한도는 ADR-020 그대로다.
**이유**: 한도를 50턴으로 낮춰도 매일 다 쓰면 월 약 $12(한글 발음·문장 뜯어보기를 더하면 약 $20)로, 9,900원(부가세·카드 수수료를 빼면 약 $6)보다 크다. 14,900원은 수수료를 빼면 약 13,100원(약 $9.4)이다. 2026-10-19 운영자가 정했다.
**트레이드오프**: 매일 한도를 다 쓰는 사용자에게는 여전히 적자라, 결제를 붙이기 전에 프롬프트 캐싱을 적용해 실측하고 가격과 한도를 다시 본다. MVP는 표시 가격을 보여 주고 `pro_clicked`로 Pro 관심을 재므로, 가격이 오르면 이 지표가 낮게 나올 수 있다. 약관의 가격 문구도 바뀐다. DB 변경은 없다.

### ADR-022: 랜딩을 "처음이어도 괜찮아요 → 대화하다 막히면 → 매일 조금씩" 순서로 다시 짠다
**결정**: 디자인 톤(색·글꼴·말풍선)은 그대로 두고, 기능 3개 섹션과 가나 밴드를 학습자가 겪는 순서의 섹션 3개로 바꾼다. 히어로 메시지는 "대화하면서 익힌다"이고, 대화 미리보기는 영어/일본어 탭으로 한국어 입력 → "이렇게 말하면 돼요"를 보여 준다. 비교표에 대화 상황 수와 AI 정답 설명 행을 더한다(`ui.md` "랜딩").
**이유**: 랜딩이 2026-10-08 뒤로 바뀌지 않아 한국어 입력·문장 뜯어보기·듣기·후리가나·한글 발음·상황 잠금과 Free/Pro 상황 수가 빠져 있었고, 예로 든 "길 묻기"는 ADR-019로 Pro 상황이 됐다. 첫 화면에서 한국어로 말해도 된다는 것과 일본어 읽기 도우미를 보여 주면 초보·일본어 입문자의 "나한테 맞나?"에 바로 답한다. 2026-10-19 운영자와 brainstorming으로 정했다.
**트레이드오프**: 탭 전환 때문에 랜딩에 클라이언트 컴포넌트(`LandingPreview`)가 하나 생긴다. 미리보기의 일본어 문장·한글 발음은 AI가 턴마다 만드는 것이 아니라 고정 문구라, 바꿀 때마다 사람이 검수한다(처음 문구는 2026-10-19 운영자가 확정). 로그인 전 클릭은 추적하지 않아 어느 섹션·탭이 가입에 도움이 됐는지는 알 수 없다(가입 수만 본다).

### ADR-023: 대화에서 배운 단어를 쓰게 유도한다 (첫 답장 때 AI가 상황에 맞는 단어를 고른다)
**결정**: 대화 세션의 첫 턴에서 예약 RPC가 세션 언어로 오늘 배운 단어(없으면 7일 안에 배운 단어)를 최대 20개 후보로 주고, AI가 그 상황에 어울리는 단어를 최대 5개 골라 세션의 목표 단어로 저장한다. 그 뒤 턴마다 AI가 아직 쓰지 않은 목표 단어를 사용자가 말하게 유도하고, 사용자가 쓴 목표 단어를 함께 알려 준다. 대화방 상단에 단어 줄, 종료 피드백에 쓴 개수와 목록, 단어 회차 결과 화면에 [대화하러 가기]를 둔다(`docs/spec/chat.md` "배운 단어 써 보기").
**이유**: 단어 학습과 대화가 따로 돌아가서 카드로 본 단어를 직접 말해 볼 기회가 없었다. 직접 말해 보면 오래 기억하고, 단어를 학습한 사람이 대화까지 하면 하루 학습이 하나로 이어진다(2026-10-19 운영자와 brainstorming). 단어는 빈도 순이라 주제가 없어 상황과 맞지 않는 단어가 섞인다(카페 주문에 犬·猫). 억지로 다 넣으면 롤플레이가 약해지므로 맞는 것만 고르고, 같은 날 다른 상황에서는 아직 쓰지 않은 단어를 먼저 후보로 준다. 세션을 만들 때가 아니라 첫 턴에 고르는 것은 첫 마디가 고정이라 그때 Claude를 부르지 않기 때문이다. 세션 생성 때 부르면 입장이 느려지고, 턴으로 세지 않는 AI 호출이 생겨 세션을 여러 번 만들면 한도 없이 AI를 부를 수 있다. 첫날이나 대화부터 하는 날에도 쓰도록 오늘 단어가 없으면 최근 7일 단어로 대신한다. 썼는지는 활용형·다른 표기(美味しい/おいしい)를 인정해야 해서 문자열 비교가 아니라 AI가 판단한다.
**트레이드오프**: 첫 마디 화면에는 줄이 없고 첫 답장부터 나타난다. AI가 쓴 단어를 잘못 판단하거나, 맞지 않는 단어를 고르거나, 유도가 억지스러울 수 있다. 프롬프트로만 정하므로 구현 뒤 실제 대화로 확인한다. 목표 단어가 있는 턴은 입력이 약 570토큰(첫 턴 약 910토큰) 늘어 턴당 약 $0.0013(첫 턴 약 $0.002), 일본어 턴 비용의 약 5분의 1이 더 든다(2026-10-20 실측. 처음 추정은 10%). 첫 턴이 이미 끝난 세션(기능 전에 대화를 시작한 세션 포함)에는 줄이 없다. DB 컬럼 3개(`chat_sessions` 2개, `chat_turns` 1개)와 `begin_chat_turn`·`finish_chat_turn` 변경으로 운영 DB에 마이그레이션을 먼저 적용해야 한다. 새 이벤트는 두지 않아, 기능의 효과는 저장된 쓴 단어로 따로 분석해야 한다.

### ADR-024: Free 하루 대화 한도를 20턴에서 10턴으로 낮춘다
**결정**: Free의 하루 AI 대화 턴을 20에서 10으로 낮춘다. 한 세션의 최대 턴(20), Pro 50턴, 새 단어 한도, 표시 가격은 그대로다. 판정하는 DB 함수 `chat_turn_limit`과 화면이 쓰는 `PLAN_LIMITS`를 함께 바꾼다.
**이유**: Free 사용자가 매일 20턴을 다 쓰면 월 약 $5(한글 발음·문장 뜯어보기를 더하면 약 $8)로, Pro 실수령(14,900원에서 부가세·카드 수수료를 뺀 약 $9.4)에 가깝다(`usage.md` "비용 추정"). Pro와의 대화량 차이도 2.5배에서 5배로 커진다. 10턴도 하루 대화 목표(성공 턴 3개 이상인 세션)보다 크다. 수요 검증 실험을 시작하기 전(구글 OAuth 동의 화면 게시 전)이라 관찰 전에 기준을 바꾸는 것이다. 2026-10-20 운영자가 정했다.
**트레이드오프**: 한 세션은 그대로 최대 20턴이라 Free 사용자는 길게 대화하면 세션 중간에 한도에 닿는다. 11번째로 보낸 문장은 실패 말풍선으로 남고 입력창 자리에 한도 안내가 나온다. [대화 끝내기]로 피드백을 받거나 다음 날 이어 간다. Free 세션을 10턴으로 줄여 자동 종료하는 안은 세션 최대 턴이 플랜에 따라 달라져 RPC와 화면이 더 바뀌고, 세션을 나눠 쓰면 여전히 중간에 끊겨서 택하지 않았다. 대화 한도 도달(`feature = chat`)이 더 자주 일어나 체험 전환율의 분모가 커진다. 약관·랜딩·계정의 Free 한도 문구도 바뀐다(`PLAN_LIMITS`에서 가져온다). 함수 본문만 바뀌어 옛 코드와 함께 돌아가지만, 운영 DB에 마이그레이션을 먼저 적용한다.

### ADR-025: 종료 피드백의 고칠 점은 예문을 따로 받고, 일본어 입문~중급은 예문에 한글 발음을 붙인다
**결정**: 종료 피드백의 `improve`를 문자열 배열에서 `[{ point, example }]`로 바꾼다. 모든 언어·레벨에서 설명(`point`) 아래에 예문(`example`)을 한 줄로 따로 보여 주고, 일본어 입문~중급은 Claude가 예문마다 `example_pron_ko`를 함께 만들어 예문 아래에 한글 발음을 둔다(중급도 항상 보인다). 옛 문자열 피드백은 마이그레이션하지 않고 전처럼 한 줄로 그린다. 같은 때 대화방은 턴이 확정되거나 끝난 결과를 받으면 `router.refresh()`로 화면 데이터를 다시 읽는다(`docs/spec/chat.md` "세션 종료 피드백", `docs/spec/journey.md` "예외 흐름").
**이유**: 고칠 점의 예문은 사용자가 따라 말해 볼 문장인데, 문자열 하나에 설명과 섞여 있어 발음을 붙일 자리가 없었고 가나를 다 읽지 못하는 입문자는 소리 내어 읽을 수 없었다(2026-10-20 운영자의 로컬 확인). 예문을 따로 받으면 영어도 예문이 눈에 띄고 프롬프트·화면이 한 모양이다. 피드백에는 번역 토글이 없어 중급만 숨기려면 새 버튼이 필요하므로 항상 보인다. 다시 읽기는 같은 확인에서 찾은 버그 때문이다: Next.js는 뒤로/앞으로 가기에서 페이지 데이터를 서버에 다시 묻지 않고, 대화방이 받은 턴과 목표 단어는 화면 상태에만 있어서, 끝낸 뒤 뒤로 가기로 돌아오면 처음 연 화면(턴 0)이 보이고 0턴 피드백이 그려졌다. 끝낼 때만 다시 읽으면 대화 도중 뒤로 가기로 돌아온 화면은 여전히 처음 연 대화를 보여 주므로 턴마다 다시 읽는다.
**트레이드오프**: 일본어 입문~중급 피드백은 표기 규칙 입력과 발음 출력이 더해져 세션당 약 $0.003이 더 든다. 화면은 옛 형식과 새 형식 두 모양을 계속 그려야 한다. 턴이 확정될 때마다 페이지를 한 번 더 렌더링해 서버 요청(인증·대화방 읽기)이 턴당 1번 늘어난다. 화면은 기다리지 않는다. 운영 DB 변경은 없다.

### ADR-026: 대화 턴에 요청 단위 자동 프롬프트 캐싱(5분)을 건다
**결정**: 대화 턴 호출에만 `cache_control: { type: "ephemeral" }`(자동 캐싱, 5분 TTL)을 더한다. 프롬프트 문구와 구조는 바꾸지 않는다. 종료 피드백과 AI 정답 설명에는 걸지 않는다(`docs/spec/backend.md` "프롬프트 캐싱").
**이유**: 대화 턴은 매번 시스템 프롬프트(1,400~2,600토큰)와 앞 대화를 다시 보내서, 같은 앞부분을 입력가의 1/10로 읽으면 품질 변화 없이 비용이 준다. 2026-10-20 실측(Sonnet 5.5, 세션 5개 30턴, 턴 사이 대기 없음)에서 첫 턴을 뺀 25턴 중 20턴이 캐시를 읽었고 턴 비용이 25% 줄었다(턴당 $0.0123 → $0.0092). 놓친 5턴은 모두 시스템 프롬프트가 바뀐 턴(한국어 입력 안내가 처음 생기거나 없어진 턴, 후보를 고른 첫 턴 다음)이다. 자주 바뀌는 안내를 대화 끝으로 옮기는 안은 AI가 받는 지시의 위치가 바뀌어 답을 다시 비교해야 하고, 실측에서 더 줄일 수 있는 몫이 턴 비용의 10% 안팎이라 지금은 하지 않는다. 종료 피드백은 세션마다 한 번이라 다시 읽을 일이 없고, AI 정답 설명은 시스템 프롬프트(약 400토큰)가 최소 캐시 길이(512토큰)보다 짧다.
**트레이드오프**: 시스템 프롬프트가 바뀐 턴과 세션 첫 턴은 쓰기 할증(입력가의 1.25배)을 내서 캐싱이 없을 때보다 조금 비싸다. 사용자가 다음 말을 5분 넘게 고민하면 캐시가 사라져 그 턴도 첫 턴처럼 쓴다. 캐싱 뒤 턴 비용의 약 64%는 출력(thinking 포함)이라, 더 줄이려면 출력 쪽(예: 문장 뜯어보기를 누를 때만 만들기)을 봐야 한다. Pro 사용자가 매일 한도를 다 쓰면 여전히 월 약 $15로 표시 가격(월 14,900원)보다 크다.

### ADR-027: 문장 뜯어보기는 처음 열 때 그 문장만 AI로 만들어 저장한다
**결정**: 대화 턴 응답에서 `reply_breakdown`·`correction.breakdown`을 빼고, 턴 프롬프트의 뜯어보기 지시도 뺀다. 사용자가 [문장 뜯어보기]를 처음 누를 때 `POST /api/chat/sessions/[id]/breakdown`이 그 문장(AI 말풍선 또는 교정 문장) 하나의 뜯어보기를 대화와 같은 모델·effort로 만들어 `chat_turns`에 저장한다. 저장본이 있으면 AI를 부르지 않는다. 같은 문장을 동시에 요청하면 "만드는 중" 표시(90초 기한)로 하나만 AI를 부르고, 나머지는 409다. 입력은 언어·상황 이름·문장이고, 언어마다 같은 시스템 프롬프트에 캐시 표시를 단다(2026-10-21 실측 뒤 더함). 따로 한도는 두지 않고, 실패는 `chat_failed`(`kind: breakdown`)로 남겨 하루 실패 10회를 함께 쓴다. 번역·한글 발음은 지금처럼 턴마다 만들고, 첫 마디는 그대로 `scenarios.ts`다(`docs/spec/chat.md` "처음 열 때 만들기").
**이유**: 2026-10-20 출력 구성 실측(실제 클라이언트로 레벨별 2턴, 10턴)에서 thinking은 10턴 모두 0이었다. 뜯어보기는 턴 출력의 54%였다(평균 541토큰 중 292토큰, 레벨별 45~61%). 턴마다 만들면 열어 보지 않는 문장에도 턴당 약 $0.003이 든다(캐싱 뒤 턴 비용 약 $0.009의 약 30%). 처음 열 때 만들면 1회 약 $0.003(추정)이라 문장의 약 70% 미만을 열면 이득인데, 뜯어보기는 궁금할 때만 여는 기능이다. 구현 뒤 2026-10-21 실측에서 1회는 약 $0.004였다. 입력 약 1,000토큰이 구조화 출력 스키마를 포함해서다. 그래서 언어마다 같은 시스템 블록을 캐시하고 상황 이름과 덩어리 지시를 넣어 약 $0.0025로 낮췄다(캐시를 읽을 때 70% 미만이면 이득, 못 읽으면 약 30~55% 미만, `docs/spec/usage.md`). 턴 출력은 평균 541 → 316토큰이 됐다. 턴 출력이 줄어 턴 응답도 빨라진다. 번역(중급 이상, 턴당 약 80토큰)과 일본어 중급 한글 발음(약 68토큰)도 같은 방식을 검토했지만 하지 않았다. 누를 때마다 지시문 입력이 새로 들어(발음은 표기 규칙 약 1,000토큰) 열람 비율이 각각 약 60%·30% 미만이어야 이득이고, 번역은 중급 이상의 기본 도움이라 자주 열 수 있다. thinking 끄기도 줄일 것이 없어 하지 않았다. 표시 없이 저장만 하면, 같은 문장을 스크립트로 동시에 여러 번 보낼 때 저장 전에 모두 AI를 부른다. 그 호출은 세지 않아 실패 10회로도 막지 못한다(2026-10-20 설계 검토). 그래서 같은 문장에는 한 번에 하나만 부르게 했다. 계정당 하루 생성 횟수 상한은 새 한도 안내가 필요하고, 지난 대화를 많이 다시 열면 닿을 수 있어서 택하지 않았다. 2026-10-20 운영자가 정했다.
**트레이드오프**: ADR-018이 피하려던 대기가 생긴다. 문장마다 처음 열 때 약 2~3초(추정) 기다린다. 문장을 대부분 여는 사용자는 지시문 입력만큼 지금보다 조금 더 든다. 따로 부르는 호출의 API·RPC·실패 규칙과 화면 상태(대기·오류)가 새로 생긴다. 뜯어보기 실패도 하루 실패 10회에 들어가 그날 대화 입력까지 막을 수 있다(2026-10-20 실측 30턴에서 뜯어보기 검사 실패는 0). 같은 문장을 두 화면에서 동시에 열면 한쪽은 "만드는 중" 안내와 [다시 시도]를 본다. 서버가 중간에 멈추면 그 문장은 최대 90초 동안 열리지 않는다. `chat_turns`에 기한 열 2개가 생긴다. 기능 전의 턴과 턴마다 만들던 때 검사에 실패한 문장에도 이제 토글이 생기고, 열면 만든다. 새 RPC가 생겨 운영 DB에 마이그레이션을 `main` push보다 먼저 적용해야 한다.
